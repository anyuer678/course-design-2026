# 08 · 体系结构（B17）

> 回答三个问题：**这个系统怎么分层、谁能依赖谁、状态机到底归谁**。
> 用例固定用 B15/B16 已经跑通的那一条：**学生提交报修 → 管理员派单**（UC-01 + UC-02）。
>
> 本文档里的两张表（依赖方向、风格指标）是**规范性且可核对的**：
> `checks/check_arch.py` 会用 `ast` 扫真实 import、用 `arch/style_probe.py` 实测指标，
> 与文档做双向相等比较。**这张图不是画出来的，是测出来的**——改了代码不改文档，或者反过来，都会红灯。

## 1. 约束（不是我的偏好，是前几轮定下的）

| 来源 | 约束 |
|---|---|
| PLAN 批次 5 | Spring Boot **分层单体** + 一个关系数据库 + 原生 HTML/CSS/JS；先做单体，不先建微服务 |
| PLAN 批次 5 | B15–B22 共用本目录，**不把同一套业务重写三遍**；微服务与内存事件总线只做原型级对比 |
| IF-01 | 认证由外部提供，本系统不保存口令 |
| IF-03 | 时间由调用方注入（NFR-05），领域层不读时钟 |
| NFR-02 | 权限判定只在服务端；前端隐藏按钮不算防线 |
| FR-15 / BR-06 | 状态变更必须留痕，且留痕不可篡改 |
| ADR-02 | 状态机的**判定源只能有一份**（本仓库里就是 `spec/workorder.py`） |

## 2. 风格比较（同一个用例，实测指标）

指标是**结构计数**，不是性能数字；`arch/style_probe.py` 跑一次不到 0.1 秒，
不要拿它当"微服务快还是单体快"的证据——那不是本题要回答的问题。

| 风格 | 参与者 | 事务边界 | 判定源份数 | 总线消息 | 重复状态点 |
|---|---|---|---|---|---|
| A 分层单体 | 1 | 1 | 1 | 0 | 0 |
| B 端口-适配器 | 2 | 2 | 1 | 0 | 0 |
| C 两服务+事件总线 | 2 | 4 | 1 | 3 | 1 |

怎么读这张表（这才是比较的意义）：

* **判定源份数三种风格都是 1** —— 因为我故意让 B、C 两套壳都调用同一个 `spec.apply_transition()`。
  这正是要传达的点：**换风格不等于复制状态机**。哪天有人在派单服务里写了
  `if state == "SUBMITTED"`，这个数会变 2，`check_arch.py` 当场红灯。
* **C 的"重复状态点 = 1"不是设计缺陷，是它的固有代价**：派单服务为了显示状态必须自留一份副本，
  而副本一旦存在，**消息顺序就开始决定正确性**。对照里我特意把那条 `submitted` 事件迟到投递一次，
  副本立刻从 `ASSIGNED` 被写回 `SUBMITTED`。分层单体里同样的"旧请求晚到"最多撞上一次行锁，不会静默改错。
* **事务边界 1 → 4**：跨服务后，"提交 + 派单"这件事不再有一个天然的原子边界，
  要靠幂等 + 补偿或 outbox 去兜。这三处细节 B18 真做微服务时才需要，本期只登记为代价。
* **B（端口-适配器）比 A 多一个参与者但没有多副本**：它买到的是"领域不依赖传输与存储"，
  代价是接线更啰嗦。**本期结论：单体 + 端口化领域**（见 ADR-01、ADR-02）。

## 3. 分层与职责边界

```
        ┌──────────────────────────────────────────────────────┐
  界面  │ 原型 web（原生 HTML/CSS/JS，B16）→ B18 换 Thymeleaf/静态 │  只渲染，不判规则
        └───────────────────────────┬──────────────────────────┘
                                    │ HTTP/JSON（读服务端给的 attemptable / required_inputs）
        ┌───────────────────────────▼──────────────────────────┐
  接口  │ Controller：参数绑定、身份注入、状态码映射（400/404/409…）│  不做业务判断
        └───────────────────────────┬──────────────────────────┘
                                    │ 方法调用（同进程）
        ┌───────────────────────────▼──────────────────────────┐
  应用  │ Service（用例编排）：开事务、取工单、调领域、写留痕      │  事务边界在这一层
        └───────────────────────────┬──────────────────────────┘
                                    │
        ┌───────────────────────────▼──────────────────────────┐
  领域  │ 状态机 + 权限 + 前置条件 + 字段规则 = **唯一判定源**      │  不 import 任何外壳
        └───────────────────────────┬──────────────────────────┘
                                    │ 端口（Repository / Clock / Identity）
        ┌───────────────────────────▼──────────────────────────┐
  基础  │ JPA/关系库、日志脱敏、配置                           │  适配器，可换
        └──────────────────────────────────────────────────────┘
```

各层"必须会做"和"绝对不做"：

| 层 | 必须做 | 绝不做 |
|---|---|---|
| 界面 | 呈现四态；把服务端给的错误码映射成中文说明；键盘可达 | 自己推按钮可不可点（B16 第 9 条踩坑）；自己判权限 |
| 接口 | 校验"是不是合法 JSON/参数形状"、注入身份、选状态码 | 决定业务是否允许（那是领域的事） |
| 应用 | 开/提交事务；把一次用例编排成若干次领域调用；写留痕 | 塞业务分支（`if 状态 == X` 出现在这层就是信号） |
| 领域 | 状态转换、权限、前置条件、字段规则、SLA 计算 | import HTTP/数据库/时钟/界面（`check_arch.py` 会抓） |
| 基础 | 持久化、脱敏日志、配置读取 | 反过来被领域依赖 |

## 4. 依赖方向（规范性）

`允许依赖` 只列**内部组件**和外部库 `netlab`（B11 的 HTTP 层）；标准库不计入。
`checks/check_arch.py` 用 `ast` 扫全仓库真实 import，与这张表做双向相等比较。

| 组件 | 允许依赖 |
|---|---|
| `spec` | — |
| `prototype` | `spec`, `netlab` |
| `checks` | `spec`, `tools`, `arch` |
| `tools` | `spec`, `checks` |
| `arch` | `spec` |
| `tests` | `spec`, `checks`, `tools`, `arch`, `prototype`, `netlab` |
| `demo` | `spec`, `checks`, `tools`, `arch`, `prototype`, `netlab` |
| `say` | — |

三条不成文但更要命的规矩：

1. **`spec` 的出边必须是 0**。它一旦开始 `import netlab` 或 `import time`，
   领域层就从"规则的唯一出处"降级成"其中一种写法"。核对器把这条单独查了一遍。
2. **外壳之间不许横向依赖**。`prototype` 不能 import `tools`，界面不能 import 契约文件——
   它们只能各自依赖领域。横向边一多，B18 换 Java 时就没人能判断哪块能一起搬走。
3. **契约文件是"出口"，不是"入口"**。`contracts/workflow.json` 由文档生成、供 B18/B20 消费；
   仓库内部谁也不许反过来靠读它拼规则（那样文档一改要先重生成才能跑，等于把编译期检查变成运行期）。

## 5. 关键机制：状态机怎么保证不被写三遍（B16 遗留问题）

这是本轮最该回答的问题。答案是**一份判定源 + 一份导出契约 + 三个方向的核对**：

```
docs/02-srs.md 三张表
   │  tools/export_contract.py（文档是唯一出处）
   ▼
contracts/workflow.json ──── B18 的 Java 实现、B20 的测试读它
   │  check_arch.py / export_contract.py --check
   ▼
spec/workorder.py（Python 侧判定源，B16 原型直接调它）
```

* 文档改了没重生成契约 → `--check` 过期红灯；
* 文档改了没改 `spec` → 导出时的三方比对红灯；
   （同一条链路在 B15 的 `check_docs.py` 里也有，所以文档↔模型↔矩阵↔契约四者互为约束）
* 有人在别处（Java 或前端）自己写了一份转换表 → 契约与实现的对拍测试红灯（B20 落地；
  本期先把"Python 侧只有一份"这条测住了）。

## 6. 横切关注点放在哪

| 关注点 | 位置 | 理由 |
|---|---|---|
| 事务边界 | 应用层 Service 方法上 | 领域函数是纯的（不可变工单 + 注入时间），事务只是外面那圈壳 |
| 留痕（FR-15） | 应用层在事务内追加，历史表只增不改 | 放领域层会让领域依赖存储；放接口层会被绕过 |
| 权限判定 | 领域层（`attemptable`/前置条件），接口层只做映射 | NFR-02：换谁问都是同一个答案 |
| 日志脱敏 | 基础设施层（切面），且**接口层不得把联系方式记进日志** | B18 实现；本期把边界画出来，避免"日志里全是手机号" |
| 配置（含 AQ-02/AQ-03 阈值） | 基础设施层读入，注入给领域 | 裁决未定的值**不进代码常量**，只进配置位，改它不该重新编译 |
| 幂等与重试 | 目前**不做**（单体同进程不需要）；若上消息才需要 | 见第 2 节 C 的代价，别提前买复杂度 |

## 7. 失败与并发（架构层面怎么兜）

* **同一工单被两个人同时操作**：以"状态 + 期望前态"做条件更新（乐观锁）。
  领域侧已经保证非法转换必抛错且不改动对象，所以冲突时最多是一方拿到 `NO_SUCH_TRANSITION`，
  不会出现"两个都成功"。这条在 B18 用 `@Version` 落地，B20 用并发测试验。
* **越权请求**：接口层拿到身份后**总是**走领域判定，不因"前端说可以"而放行；
  返回 403/400 时不改状态（B16 原型已经这样测了）。
* **留痕写入失败**：与状态变更同事务，一起回滚——不允许出现"状态变了但没记录"。
* **阈值待定（AQ-02 / AQ-03 / AQ-12）**：架构上留配置位与端口，**不给默认实现打勾**。
  裁决前这些行为不可测试，写清比写错好。

## 8. 明确不做（防止下一轮顺手加戏）

* 不拆微服务、不引入消息中间件、不做服务注册发现（第 2 节的 C 只是内存原型对照）。
* 不做多数据源、不做分库分表、不做 CQRS 读模型——单量与查询复杂度都还没到。
* 不做领域事件外发（通知属 IF-02，未裁决范围）。
* 不在 B17 写任何 Java 代码：本层的产物是**结构与契约**，实现属 B18。
