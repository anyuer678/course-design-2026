# ADR-01 · 先做分层单体，不做微服务

- 状态：accepted
- 日期：2026-10-01
- 相关：PLAN 批次 5、`docs/08-architecture.md` 第 2 节、FR-05~FR-14、IF-04

## 背景

报修系统的业务主线是"学生提单 → 管理员派单 → 维修员接单/完工 → 学生验收 → 三类查询"。
B15 已经把它写成一台可执行的状态机（15 条转换、12 个动作、3 个角色），B16 用原型验证了这条链路走得通。
现在要定 B18 用什么结构落地。PLAN 批次 5 已经把技术形态写死为
"Spring Boot 分层单体 + 一个关系数据库 + 原生 HTML/CSS/JS"，但**为什么不是微服务**这件事
不能靠"计划里这么写的"，得有一次可查的比较——尤其因为这个仓库后面还有 B19（SOA）会引入多接口。

`arch/style_probe.py` 把同一个用例（提交 → 派单）在三种结构下各跑一遍，测出：
分层单体 1 个参与者、1 个事务边界、0 条消息、0 个重复状态点；
两服务 + 内存事件总线 2 个参与者、**4 个事务边界**、3 条消息、**1 个重复状态点**。
其中"重复状态点"那条不是理论担忧：对照里把一条 `submitted` 事件迟到投递，
派单服务的副本立刻从 `ASSIGNED` 被写回 `SUBMITTED`。

## 决定

**采用分层单体**，四层：接口（Controller）→ 应用（Service，事务边界）→ 领域（状态机与规则，唯一判定源）
→ 基础设施（持久化、脱敏日志、配置）。领域层通过端口（Repository / Clock / Identity）与外壳解耦，
即 ADR-02。**本期不拆服务、不引入消息中间件。**

## 备选

1. **端口-适配器（六边形）为唯一结构**：领域更干净、可测试性更好，但对一个单进程 Web 系统来说
   接线代码明显变多；而且 B16 的原型已经证明"领域不依赖传输"这件事用依赖方向检查（第 4 节表）就能守住，
   不需要先把所有出口都抽象成端口。**采纳其精华**：领域零依赖 + 端口化时钟/存储，但整体仍是单体。
2. **两三个服务 + 内存事件总线**：能练"跨服务一致性"，但代价当场可见——事务边界从 1 涨到 4，
   出现状态副本，消息顺序开始影响正确性，还要额外背幂等与补偿。
   这些正是 B19/B30 的教学点，**该在讲它们的轮次里做**，不该在 B18 交付业务链路时顺手背上。
3. **CQRS / 读写分离**：查询需求（FR-12~FR-14）是"带筛选的列表"，一条 SQL 足够，没有引入两套模型的动机。

## 后果

**正面**：一次用例只有一个事务边界，留痕与状态变更天然原子（FR-15、BR-06 直接好验）；
并发冲突收敛为一次乐观锁失败；部署与本地走查都简单，B20 的接口测试不用起多个进程。

**负面与被接受的代价**：
- 领域逻辑与其他代码同进程，**边界只能靠约定和检查维持**，不像服务边界那样被物理强制——
  所以必须有 ADR-02 的核对器补上这道闸，否则单体一定会烂成"谁都能 import 谁"。
- 将来真要拆服务时，第 2 节 C 列的那些代价（副本、顺序、幂等）会一次性找上门。
  我们不假装它们不存在：B19 若做双接口，仍按"同一业务、两种接口"处理，不借机拆服务。
- 单体的扩展单位是整个进程，若真出现"派单量大"这类需求，答案是先量一量再谈（NFR-06 仍待验证）。

## 验证方式

- `checks/check_arch.py`：真实 import 边必须等于 `docs/08` 第 4 节声明的边集（双向相等），
  越界依赖与"文档画了但代码没有"都算失败——图不是装饰。
- `check_arch.py::check_domain_purity`：`spec/` 里出现 `netlab`/`import time`/`http` 即失败。
- `arch/style_probe.py::same_outcome()`：三种风格必须得到同一终态与同样的判定源调用次数，
  否则"比较"本身不成立，指标表也就没有意义。
- B18 交付时的验收口径：这条用例仍然只需要一次事务提交、一处状态判定源。
