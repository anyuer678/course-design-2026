# ADR-02 · 状态机判定源唯一化：领域层一份，外壳只读结论

- 状态：accepted
- 日期：2026-10-01
- 相关：`docs/08-architecture.md` 第 5 节、NFR-02、FR-15、B16 第 9 条踩坑、`spec/workorder.py`

## 背景

B16 留下一句话："按钮的可用性来自 `spec.attemptable()`，前端不自己推规则。"
这句话当时解决了具体问题（`app.js` 里不出现 `state ===` / `role ===`），但它只覆盖了一个壳。
B18 会再加两个壳：Spring MVC 的接口层，以及未来的移动端或开放接口。
**同一台状态机被抄成三份**几乎是必然结局——因为抄一份比注入一份更省事，而且抄错了也不会立刻报错，
只会表现为"界面让点、后端拒绝"或"这个端能操作、那个端不能"。

一旦真的出现多份，最难查的不是行为差异，而是**没人知道哪份是权威**：
改需求的人改了文档，测试仍然读旧的那份，绿灯照过。

## 决定

**判定源只有一份，放在领域层；所有外壳只读它的结论，不复制它的逻辑。**

三条具体约束：

1. **文档是唯一出处**：`docs/02-srs.md` 第 3/5/6 节那三张表。
2. **领域层是它的可执行形式**：`spec/workorder.py`（B18 换成 Java 后是领域模块，位置变了、角色不变）。
   外壳要"能不能点、要填什么"，调 `attemptable()` / `required_inputs()`，**不自己判**。
3. **前端与接口层只消费结论**：接口把领域抛的错误码原样映射成 HTTP 状态与中文说明；
   前端按服务端给的 `attemptable` 渲染按钮，收到 4xx 就如实显示（B16 已实现并有测试）。

配套：**判定源份数**变成一个可测指标——`check_arch.py` 用 AST 扫全仓库"定义了 `TRANSITIONS` 的模块"，
必须恰好等于 `["spec/workorder.py"]`。

## 备选

1. **让前端自己判断按钮**（最常见写法）：省一次往返，但把权限表抄进 JS，
   于是有了第二份判定源。B16 第 9 条与本轮的"份数检查"就是针对它。
2. **共享一份配置文件，各方自己解释**：仍然要每个壳写一遍解释逻辑，判定源份数照样 >1，
   只是把复制从代码搬到了"解析代码"里。所以契约必须配**导出 + 对拍**（ADR-03），不能只是一份 JSON。
3. **不做限制，靠 code review**：这个仓库没有 reviewer，只有测试。凡是"记得住就行"的方案在这里都等于没方案。

## 后果

- **正面**：需求变了只改文档 + 领域层；外壳自动跟着变。
  越权路径收敛成一条（服务端判定），B20 只要测这一条就能覆盖所有壳。
- **代价 1：会出现"点了才被拒"的按钮**。`attemptable()` 只看状态与角色，不含前置条件
  （是不是本人、理由填没填）。要让按钮精确到"点了必成功"，就得把前置条件判断复制到界面层——
  正是本 ADR 禁止的事。这个取舍是故意的，写在 `docs/06` 的 V4 里。
- **代价 2：跨语言时判定源仍是两份**（Python 与 Java 各一份实现，只是同源不同人写）。
  所以必须有 ADR-03 的契约对拍，否则"唯一"只对当前这一半成立。B20 的 JUnit 读同一份契约，就是为这个。
- **代价 3：领域层不能为了方便偷偷 import 任何东西**，一旦它为省事引入 `import time`，
  NFR-05（时间注入）和留痕顺序测试同时崩。所以 `check_domain_purity` 是独立一条检查，不靠自觉。

## 验证方式

- `check_arch.py`：`判定源份数 == 1` 且模块路径恰好是 `spec/workorder.py`（AST 扫描，不是 grep 关键字）。
- `check_arch.py::check_domain_purity`：`spec/` 内出现 `netlab`、`import time`、`datetime`、`http` 即失败。
- 依赖方向表（`docs/08` 第 4 节）与真实 import 双向相等 → 保证没有"界面被领域反向依赖"这类怪边。
- B16 已有的前端静态断言：`app.js` 不出现 `state ===` / `role ===`（规则没被复制到 JS）。
- B20 待补：Java 领域实现与 `contracts/workflow.json` 的对拍测试（同一批转换、同一批权限）。
