# ADR-03 · 把 SRS 的表导出成契约文件，供 B18/B20 消费

- 状态：accepted
- 日期：2026-10-01
- 相关：`contracts/workflow.json`、`tools/export_contract.py`、ADR-02、`docs/08-architecture.md` 第 5 节

## 背景

ADR-02 让判定源在本仓库内只有一份。但 B18 要用 Java 重做实现，B20 要给它写测试——
那时"同一份规则"会以**两种语言**存在。Python 那份和 Java 份之间，靠什么保证一致？

最自然的做法是让两边都去读 `docs/02-srs.md` 里那三张表。但 markdown 表格给人看可以，
给机器读要写一个解析器；Java 侧再写一个和 Python 侧不同的解析器，
就变成"两份解析代码 + 一份文档"，出问题时报的错谁都不信。
反过来，如果两边各自把状态表**抄进代码常量**（最常见），那 ADR-02 的"唯一判定源"
就只对 Python 那一半成立。

## 决定

**文档仍是唯一出处；契约文件是它的机器可读导出物，跨语言消费一律走契约。**

- `tools/export_contract.py` 从 `docs/02-srs.md` 现算出 `contracts/workflow.json`：
  状态、动作、转换（含角色与前置条件）、权限映射、可见性代码、SLA 小时数、字段错误码、终态集合。
- 生成前必须通过**三方比对**：文档 ↔ `spec/workorder.py` ↔ 待写出的契约。
  任何一处理解不一致，导出直接失败（不产出"看起来对"的 JSON）。
- `--check` 只判断契约是否过期，供 B21 的本地流水线用。
- B18 的 Java 领域实现、B20 的对拍测试**读契约**，不读 markdown，也不各自定义常量。
- 契约文件带 `schema_version`；本仓库内部代码**不回头读它拼规则**（它是出口，不是入口）。

## 备选

1. **两边各自解析 markdown**：省一个导出步骤，代价是两个解析器。
   解析器本身会有 bug——本轮就实际遇到两次：一个枚举正则只认大写字母把动作表读成空集合，
   一个 ID 白名单漏了 `AQ` 而冤枉了正常文档。两个语言各踩一遍，谁都不知道对方踩了。
2. **契约作为唯一出处，文档由契约生成**（先写 JSON 再生成表格）：机器友好，
   但需求评审看的是表格与文字理由，把出处反过来会让"评审过的版本"变成生成物，
   改一处要同时想清楚改的是规则还是排版。需求阶段这个方向不对。
3. **不做契约，靠 B20 人工比对**：人工比对在有两份实现之后一定会退化成"跑过的就算对"。

## 后果

- **正面**：跨语言一致性第一次有了可机械执行的判据；`--check` 让"改了文档忘重生成"当场暴露。
  B18 少写一个 markdown 解析器，B20 少写一份状态表。
- **代价 1**：多一个生成物就要多一条纪律——**不许手改 `contracts/workflow.json`**。
  `check_arch.py` 会比较"文件内容"和"由文档现算的内容"，改了必被发现，但它防的是忘，不是存心。
- **代价 2**：契约只能表达**表里写得下的东西**。文字说明（例如 V4 里"点了仍可能被拒"）
  不在契约里，跨语言时只能靠对拍测试补——所以 B20 必须真去测行为，不能只比 JSON。
- **代价 3**：文档格式变成接口。列名、取值写法一旦改动就会破坏导出，
  这是刻意的（`checks/check_docs.py` 的解析器会直接报错而不是猜），但写文档的人需要知道。

## 验证方式

- `python tools/export_contract.py --check` → 契约过期返回非 0。
- `checks/check_arch.py::check_contract` → 契约 = 文档现算 = `spec`，三方任一不符即失败。
- 导出时若文档表格有列数不一致、未知取值，`build()` 直接报错（本轮实测触发过一次：
  枚举正则漏小写导致动作表读空，导出被拒而不是产出空契约）。
- **待补（B18/B20）**：Java 领域实现与契约的转换数、动作集、权限映射逐条相等；
  以及"同一批随机操作序列在 Python 模型与 Java 实现上得到同样的转换结果"。
