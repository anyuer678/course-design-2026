# 01 · 范围与假设

> B15（软件工程基础 + 软件需求工程）的产物之一。
> 这一节先交代**需求的来源**，因为按 PLAN 第 6 节，文档型任务要验收"来源、分析和产物"，
> 而最不该做的事就是拿一份编得很像的文档冒充真实调研。

## 来源声明（先说清楚我手上没有什么）

| 来源类型 | 有没有 | 说明 |
|---|---|---|
| 真实宿舍报修调研（问卷/访谈/现场观察） | **没有** | 我没有接触过任何真实的宿管中心、维修班组或学生用户，也没有拿到任何历史报修数据 |
| 校方规章制度文件 | **没有** | 派单规则、验收时限、SLA 时长都是**我给出的教学假设**，一律登记为待裁决问题（见 05） |
| 现有系统（哪怕一张 Excel 台账） | **没有** | 因此不存在"迁移/兼容"需求，也没有旧数据字典可参照 |
| 课程计划里已固定的约束 | **有** | PLAN 第 5 节批次 5：业务主线是"学生提单、维修员接单并完工、管理员分派和查询"；技术形态定为 Spring Boot 分层单体 + 一个关系数据库 + 原生 HTML/CSS/JS；B15 从**最小提单与查询链路**开始 |
| 前几轮已经验证过的技术事实 | **有** | 输入校验、路径/协议限制、状态可核查的交付方式来自 B10/B11/B13/B14/B31 的实测教训；本项目的"文档与模型必须一致"就是把这些做成可执行核对 |

**因此本文档的性质是：给定场景下的需求分析练习。**
所有带 `AQ-` 编号的地方都是"需要真实利益相关者才能定"的判断，我替它们做了一个**可辩护的默认值**，
并在 05 里逐条写明：谁裁决、裁决前按什么走、改了会影响哪些需求。
不把默认值写成"校方规定"，是这份文档唯一的诚实底线。

## 场景（假设的最小描述）

一栋/若干栋学生宿舍的报修流程目前是线下登记：学生在宿管台口头或微信说一声，
宿管在本子上记，维修工路过时看一眼。已知痛点（**同样是假设**，因为没有观察记录）：

1. 学生不知道自己报的单子现在归谁、修没修；
2. 维修工之间靠口头交接，谁接单没有系统记录；
3. 同一间宿舍同一类问题短期内重复报修，没有提示；
4. 宿管月底要汇总"哪栋楼坏得多"，靠手翻本子。

## 在范围内（本期只做最小链路）

* 三类角色：**学生（报修人）**、**维修员**、**管理员（宿管/派单人）**。
* 一条完整链路：**提单 →（派单）→ 接单 → 完工 → 验收关闭**，加上取消、退回、查询。
* 工单的**状态与权限规则**（这是本期的核心，做成可执行核对）。
* 字段校验、重复报修检测、状态变更留痕。
* 三类查询：我的单子 / 我的任务与公共池 / 管理员条件筛选。

## 明确不在范围内（写出来，防止后续轮次顺手加戏）

| 不做什么 | 原因 | 什么时候再谈 |
|---|---|---|
| 登录、注册、密码策略 | 假设校园统一身份已存在，接口只声明"给我一个已认证的角色与工号" | B18（认证与授权） |
| 评价/评分、维修质量回访 | 与最小链路无关，且需要真实运营方定义指标 | 需求确认后另立 |
| 备件库存、采购、成本 | 范围爆炸；本期的"物料消耗"只作为完工说明的自由文本 | 不在本课设周期内 |
| 短信/推送/邮件通知 | 需要外部通道与预算 | 只做接口声明（IF-02），本期不实现 |
| 配件排期、路线优化、班组排班 | 属于调度问题，不是报修主链路 | B34 之类另说 |
| 报表大屏、月度汇总导出 | 数据量与口径都未定 | 先有查询（FR-10~12），汇总口径待定 |
| 移动端原生应用 | 场景未证明必要 | 不在范围 |
| 多语言、暗色主题 | 与需求无关 | 不在范围 |

## 利益相关者（假设的角色模型，非真实访谈所得）

| 角色 ID | 名称 | 关心什么 | 会推翻我默认值的点 |
|---|---|---|---|
| ACT-01 | 学生（报修人） | 提交简单、看得到进度、验收有发言权 | 验收超时后谁有权关闭（AQ-03） |
| ACT-02 | 维修员 | 派单清楚、能拒、不被反复打扰 | 拒单后是否立即回到公共池（AQ-04） |
| ACT-03 | 管理员（宿管） | 不漏单、能改派、能追责 | 优先级与 SLA 时长（AQ-02） |
| ACT-04 | 系统（时间来源） | 一致性：SLA 计算依赖可信时钟 | 时钟漂移与"超时"判定（AQ-05） |

> 注：ACT-04 不是人，是**依赖**。把它列进利益相关者是因为它会影响需求判定（超时、留痕顺序），
> 需求阶段假装它不存在，到 B18 就会变成"测试要 sleep 等待"的工程债——这个债我已经用
> "时间由外部注入"的写法还掉了（NFR-05）。

## 成功怎么算（本期）

本期**不交付可运行系统**，交付物是否成立由三条可核对的标准判断：

1. **一致性**：SRS 里的状态表、权限表、可见性表与可执行模型逐条一致——由 `checks/check_docs.py` 判定，
   改文档不改模型（或反之）当场红灯。
2. **可追踪**：每条功能需求至少被一个用例或用户故事引用，每条验收标准要么给出可执行的验证入口
   （测试 ID），要么明确标注"待验证 + 由哪一轮验证"，不许留空。
3. **歧义可见**：每一个我替真实用户做的判断都登记在 05，写清默认值、影响面和裁决人。
