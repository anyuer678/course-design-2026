# 03 · 用例

> B15 产物。六个用例覆盖最小链路。`覆盖需求` 行是机器读的：`checks/check_docs.py` 据此生成
> `traceability.csv`，任何一条 FR 没被用例或用户故事引用就会红灯。
>
> 用例里**不写界面**（那是 B16），只写"谁、在什么条件下、能做什么、什么情况下算失败"。

### UC-01 · 学生提交报修单

- 角色：STUDENT（ACT-01）
- 覆盖需求：FR-01, FR-02, FR-03, FR-04, FR-15, BR-01, BR-07, BR-09, IF-01, IF-03
- 前置条件：操作者已通过 IF-01 认证，角色为学生，且携带学生标识
- 后置保证：工单进入 `SUBMITTED`；`submitted_at` 与 `sla_due_at` 已按优先级表算出；历史追加一条
- 主流程：
  1. 学生填写宿舍编号、分类、优先级、描述、联系方式（可为草稿，见 FR-02）
  2. 提交 → 系统一次性校验全部字段（FR-03）
  3. 若同宿舍同分类已有未完成的单子 → 给出重复提示（FR-04），学生可坚持提交
  4. 校验通过 → `DRAFT → SUBMITTED`，记录 `submitted_at` 与 SLA 到期时刻（BR-08）
- 扩展流：
  - 4a. 学生只保存草稿不提交：状态保持 `DRAFT`，只有本人和管理员可见（SRS 第 6 节）
- 异常流：
  - 2a. 任一字段不合规则：**不产生状态变更**，一次性返回全部问题及其字段名（NFR-03）
  - 3a. 有人替别人提交（`reporter` 与操作者不符）：拒绝（BR-09）

### UC-02 · 管理员派单、改派与退回公共池

- 角色：ADMIN（ACT-03）
- 覆盖需求：FR-05, FR-06, BR-03, BR-05, IF-01
- 前置条件：工单处于 `SUBMITTED`（派单）或 `ASSIGNED`（改派/退回）
- 后置保证：`assignee` 是唯一的（BR-03）；退回公共池时 `assignee` 清空且必须已写明理由
- 主流程：
  1. 管理员查看待派单队列（可按分类、优先级、逾期筛选，见 UC-05）
  2. 指派给某位维修员 → `SUBMITTED → ASSIGNED`
  3. 派错人可改派：`ASSIGNED → ASSIGNED`，状态不变但换人并留痕（TR-03）
- 扩展流：
  - 2a. 改派：状态不变、`assignee` 变、历史新增一条（FR-06）
  - 2b. 退回公共池：`ASSIGNED → SUBMITTED`，`assignee` 清空，理由必填（BR-05）
- 异常流：
  - 1a. 未指定维修员或工号为空/超长：拒绝（`ASSIGNEE_REQUIRED`）
  - 2c. 学生或维修员尝试发起派单：拒绝（权限矩阵）

### UC-03 · 维修员接单、拒单与完工

- 角色：WORKER（ACT-02）
- 覆盖需求：FR-07, FR-08, BR-04, BR-06, IF-01
- 前置条件：工单 `ASSIGNED` 且 `assignee` 就是本人（接单/拒单），或 `IN_PROGRESS` 且 `assignee` 是本人（完工）
- 后置保证：完工后进入 `RESOLVED`，完工说明非空并进入历史
- 主流程：
  1. 维修员在"派给我的"列表里看到工单（可见性 `OWN_OR_POOL`）
  2. 接单 → `ASSIGNED → IN_PROGRESS`
  3. 现场处理完，填写完工说明 → `IN_PROGRESS → RESOLVED`
- 扩展流：
  - 2a. 拒单：`ASSIGNED → SUBMITTED`，`assignee` 清空，单子回到公共池
- 异常流：
  - 2b. 别的维修员来接单：拒绝（`ASSIGNEE`，BR-04）
  - 3a. 完工说明为空：拒绝（`NOTE_REQUIRED`）
  - 3b. 维修员想把修不动的单直接退回公共池：**本期没有这个动作**，只能由管理员 `escalate`
    （这是刻意的收紧，见 AQ-04）

### UC-04 · 学生验收，或管理员超时关闭

- 角色：STUDENT（ACT-01）、ADMIN（ACT-03）
- 覆盖需求：FR-09, FR-10, FR-15, BR-02, BR-05, BR-10, IF-03
- 前置条件：工单处于 `RESOLVED`
- 后置保证：`CLOSED` 是终态，此后没有任何出边（BR-02）
- 主流程：
  1. 学生查看完工说明 → 验收通过 → `RESOLVED → CLOSED`
- 扩展流：
  - 1a. 学生认为没修好 → 退回维修 → `RESOLVED → IN_PROGRESS`，`assignee` 保持原维修员，理由必填
  - 1b. 学生长期不验收 → 停留满验收宽限期（默认 168 小时，BR-10）后管理员强制关闭 → `RESOLVED → CLOSED`；
    未满宽限期就关是被拒绝（`ACCEPTANCE_NOT_MATURE`），不是"提醒一下但还是关掉"
- 异常流：
  - 1c. 非本人学生验收：拒绝（`OWNER`）
  - 1d. 想从 `CLOSED`/`CANCELLED` 再动它：拒绝（BR-02，`NO_SUCH_TRANSITION`）
  - 1e. 维修员自己把 `RESOLVED` 改成别的状态：权限矩阵里没有这个角色

### UC-05 · 查询工单

- 角色：STUDENT、WORKER、ADMIN
- 覆盖需求：FR-12, FR-13, FR-14, BR-09, BR-11, IF-04
- 前置条件：已通过 IF-01 认证并带有角色
- 后置保证：返回集合**恰好**是可见性矩阵所声明的那一批，不多一条也不少一条
- 主流程：
  1. 学生：我的单子（含草稿），可按状态、分类筛选
  2. 维修员：公共池（`SUBMITTED`）+ 派给我或我处理过的
  3. 管理员：全部，可按宿舍编号、分类、状态、优先级、是否逾期筛选
- 扩展流：
  - 3a. 只看逾期：排除 `RESOLVED` 与两个终态（SRS 第 8 节）
- 异常流：
  - 1a. 先筛选后收口是禁止的实现顺序：那样别人草稿的内容会通过筛选结果泄漏
    （所以 `filter_orders` 先做可见性再做条件，测试穷举样例数据核对）

### UC-06 · 取消报修

- 角色：STUDENT、ADMIN
- 覆盖需求：FR-11, BR-02, BR-05, BR-09
- 前置条件：工单处于 `DRAFT`/`SUBMITTED`（学生），或 `SUBMITTED`/`ASSIGNED`（管理员）
- 后置保证：`CANCELLED` 终态，`assignee` 清空，历史里带着理由
- 主流程：
  1. 学生取消自己的草稿或待派单单子
  2. 管理员取消已派单的单子（必须写理由）
- 异常流：
  - 1a. 已派单时学生直接取消：**不允许**（权限矩阵里 `ASSIGNED` 的 cancel 只给管理员）——
    维修员可能已经在路上了。学生应先联系管理员，或等接单后走验收退回。登记 AQ-09。
  - 2a. 管理员不写理由：拒绝（`REASON_REQUIRED`）
  - 3a. 维修中的单子想取消：本期没有该动作，只能管理员 `escalate` 退回公共池再取消
