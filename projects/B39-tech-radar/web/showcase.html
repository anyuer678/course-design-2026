# 记录：无协调多副本如何收敛——LWW-Register 与「(计数器, 副本)」全序

- 来源：示例（非真实讲座）——按 `docs/record-template.md` 写的一次完整示范，演示模板怎么用
- 日期：2026-10-02
- 记录人：课程设计仓库（B39 示例）

## 问题

多个副本各自接受写入、平时互不协调（网络分区、离线编辑、多端同步都会遇到），
**最终如何保证大家看到同一个值**？如果做不到"收敛"，用户就会遇到"我刚写的东西没了"
——这不是体验问题，是数据正确性问题。

## 原理

把"合并"设计成一个**join（取上确界）**而不是"最后一次写入赢"的任意约定：

1. 每个写操作带时间戳 `(计数器, 副本号)`——计数器在本副本内单调递增，
   副本号做破平（total order）。没有全序就没有确定的赢家，收敛无从谈起；
2. 合并函数 `merge(a, b) = 取 timestamps 较大的那个 (值, 时间戳)`；
   满足三条性质 → 收敛（不管操作以什么顺序、分几批到达）：
   - **交换律**：merge(a,b) 与 merge(b,a) 结果相同；
   - **结合律**：先合哪两个不影响最终结果；
   - **幂等性**：重复合并同一份状态不变（重传/回声不会翻车）。
   这三条性质合起来就是 join 半格——交换/结合/幂等正是"最终一致"的充分条件；
3. 向量时钟在这里的角色：给"因果"留位置（本最小复现只用它记录每副本进度，
   真正的多值语义需要 OR-Set 等更强的结构）。

**如果我错了会先错在哪里**：如果 merge 用了墙钟时间当时间戳，时钟偏斜会让
"较晚的写"在另一台机器上判定为较早——性质测试里的"置换不变性"就会红。

## 证据（如何核验）

- `projects/B39-tech-radar/repro/crdt_lww.py`，性质测试跑法：`python -m unittest discover -s tests`，
  共 18 项断言三性质 + 收敛（随机置换 100 组、种子固定）；`run.bat` 复跑两次退出码 0；
- `projects/B39-tech-radar/tests/test_radar.py` 里 `test_tie_break_by_replica`：
  两副本计数器并列时，按副本号字典序取大——手算场景逐值钉住；
- 同类问题在本仓库的两处落点（技术雷达要能挂到自己的系统里）：
  `projects/B30-mini-raft/README.md`（§5.4.2 只提交本任期条目——串行共识下的冲突处理）、
  `projects/B38-mini-redis/README.md` 与 `@f0bb729`（单机串行化=另一种"避免冲突"的路线）。

## 局限与适用边界

- 只有 LWW-Register：**丢失并发写**（两个副本同时写不同值，合并后必有一方被覆盖）。
  要保留并发值得换 OR-Set / MV-Register：代价是读到的可能是"多个值需要应用层合并"；
- `(计数器, 副本号)` 全序要求副本号**可判定且全局唯一**；跨组织系统里这一步往往
  比算法本身难（命名空间/证书）；
- 计数器是逻辑计数、不是墙钟——无法回答"最后写发生在几点"；
- 没有因果投递保证：任意乱序最终都会收敛，但**中间状态**可能违反直觉；
- 本复现是单进程模拟（消息投递顺序由测试编排），不是真实网络。

```
python -m unittest discover -s tests     # 18 项：性质 + 收敛 + 检查器正负例

```

`并列计数器的赢家` 行显示 `'b'（时间戳 (1, 'b') 战胜 (1, 'a')）→ 值 'y'`。

怎么自己跑

  • run.bat：三步（测试 → demo → 展示页新鲜度）；python demo.py 只看演示。

  • python tools\showcase.py --write：重新生成本页；--check 重算比对、过期即红。

生成物：python tools/showcase.py --write（口径见 showcase/SPEC.md； 仓库级校验 python showcase/check.py）。页面数据全部现算，无外部请求。
