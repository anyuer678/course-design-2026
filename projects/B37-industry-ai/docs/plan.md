# B37 行业方案书：设备故障预测基线（模拟数据，不外推生产）

> 课程：行业软件前沿应用 + 大型行业软件创新实践。
> 本方案书的**一切数字来自合成数据**（程序生成遥测 + 注入故障），
> 只用于演示"方案怎么立项、口径怎么定、账怎么对"；**不得外推为真实产线效果**。

## 1. 场景与目标

- 场景：一支 10 台设备的产线车队，已有（B35 体系的）遥测上报：温度、振动，
  逐条读数带数据质量事件账本（spike 尖峰 / freeze 卡值 / dropout 断数）。
- 目标：在**故障发生前**给出告警——不是"事后检测异常"，而是"预测性维护"：
  提前 horizon 步预警，给维护排班留窗口。
- 两个代价要摆上台面（本项目的评估立场）：
  - **漏报**（故障没被预警）：非计划停机，代价高；
  - **误报**（报警但无事）：现场检查成本 + 告警疲劳，报警一多，人就不看了。
- 因此交付物不是"一个高 AUC 的模型"，而是**一条可调、可对账的告警流水线**：
  概率分数 → 阈值（运营选点）→ 告警，外加逐条可追溯的误报/漏报解剖。

## 2. 数据

| 项 | 口径 |
|---|---|
| 规模 | 10 台设备 × 480 步 = 4800 条读数（`Config` 单点可调，测试与演示共用） |
| 基线信号 | 各设备温度 70±6°C（安装点差异）附近的 OU 均值回复序列；振动 0.5 附近 |
| 数据质量事件 | B35 口径：spike（单点离群 +35°C，3%）、freeze（重复上一条，3%）、dropout=0（见下） |
| 退化/故障 | 每台 3 次：故障前 24 步线性恶化（过热 +1.6°C/步 或 磨损 +0.09 振动/步），故障后 5 步恢复 |
| 账本 | 每类事件逐条计数 + `sent` 对账（与读数行逐类相等，测试钉死：spike 147 / freeze 142 / sent 4800） |
| 为什么 dropout=0 | 断数会造成缺行、窗口与账本对不齐；B35 已把断数的完整性账本讲透，此处聚焦"读数存在但设备在退化" |

**声明**：以上全部为合成数据；B35 的 `SensorSimulator` 因长时线饱和（480 步温度均值
141.3°C、18.3% 夹取，见项目 README 与 `test_b35_simulator_saturates_on_long_runs`）
只被复用其分类学/账本/schema，信号生成换为 OU + 单点尖峰。

## 3. 方法

- **特征**（8 维，滑动窗口 W=8、步进 6）：温度/振动的均值、最小二乘斜率、极差、标准差
  （斜率用回归而不是首尾差——抗单点尖峰）。
- **标签**：窗口末端 t 的未来 horizon=24 步内（不含当步）会发生故障 ⇒ 1。
  故障已发生到恢复结束（t ∈ [f, f+W+decay−1]）的窗口**排除**——读数还在高位，
  标 0 会教模型学噪声。两个口径都有逐边界测试。
- **切分**：按设备（训练 0..7，测试 8/9）——部署时面对的就是没见过的设备。
  随机切分作为对照臂同时报告（本数据上两口径接近，如实登记）。
- **模型**：
  1. 固定阈值（铭牌 100°C / 2.0）：不动点的对照基线；
  2. B23 手写决策树（复用，熵准则，depth=4）；
  3. 本项目手写逻辑回归（sigmoid + 交叉熵 + L2；GD 与 Newton/IRLS 双实现互拍，
     数值梯度检查 2.8e-11）。
- **评估**：混淆矩阵 + 精确率/召回率/F1；阈值扫描曲线；ROC/AUC；
  **提前量**（只认 [f−horizon, f−1] 内首次报警，lead = f − t）。

## 4. 评估结果（模拟数据）

| 模型（best-F1 运营点） | 报警 | 精确率 | 召回率 | F1 | AUC |
|---|---|---|---|---|---|
| 固定阈值（100°C / 2.0） | 29 | 0.310 | 0.375 | 0.340 | — |
| B23 决策树（thr 0.14） | 20 | 0.950 | 0.792 | 0.864 | 0.899 |
| 手写逻辑回归（thr 0.50） | 18 | 1.000 | 0.750 | 0.857 | 0.926 |

- **阈值敏感性**：召回≥95% 需把阈值降到 0.02（111 条报警、精确率 0.207）；
  告警预算 ≤24 条时运营点为 0.22（P 0.833 / R 0.833）。AUC 是排序质量，
  选点是运营决策——两者分开汇报。
- **误报解剖**：固定阈值的 20 条误报**全部**发生在含 spike/freeze 的窗口（20/20）；
  阈值报警的误报源头首先是数据质量，不是模型。
- **漏报与提前量**：树在运营点 6/6 接住测试设备的全部故障，提前 16–19 步
  （上限为 horizon=24）；overheat 1/1、wear 5/5。
- **切分口径**：设备切分 AUC 0.926/0.899，随机切分 0.848/0.868——
  本数据上未见随机切分虚高，但部署口径必须按设备（新设备没有历史）。

## 5. 运营建议（从本方案能带走的）

1. **先治数据质量，再调模型**：误报归因表（`fp_context`）应作为常态报表——
   若误报集中在 spike/freeze 窗口，优先修采集侧（滤波/标定），比换模型便宜。
2. **阈值按"告警预算"选**：运维能处理的告警条数（本示例 ≤24）决定运营点；
   best-F1 只是数学最优，不是运营最优。
3. **提前量是业务给的**：horizon=24 是本示例的假设；维护排班周期多长，
   horizon 就多长——它是需求参数，不是模型超参。
4. **每次换特征/换模型，账本对账不能省**：数据账（行数 vs 账本）与样本账
   （窗口/正负/排除）先对平，再谈指标。

## 6. 局限与外推禁令

- 全部数据为合成；故障模式（线性恶化、固定 horizon）是简化假设，
  真实退化常带非线性与突变——**本项目任何数字不得外推为真实产线效果**。
- 未做：RUL（剩余寿命）回归、生存分析、在线学习与漂移监控、多传感器融合、
  与 sklearn/库模型对拍（需安装，未获批准）。
- 因果性：模型学的是"与本仿真故障过程的统计关联"，不是物理因果；
  真实部署需重新采集、标定、再验证。

## 7. 复现

```
run.bat                    # 27 项测试 + 六段演示（build\ 下 3 张 SVG）
python demo.py             # 只跑演示，全部数字现算
```

种子化：设备基线/游走/异常/故障时间表/切分全部由 `fault/config.py` 的 `seed_base`
派生，两次运行逐值一致（`tools/logdiff.py` 可核对两次 run.bat 日志）。
