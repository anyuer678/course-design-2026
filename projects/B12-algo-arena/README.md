# B12-algo-arena —— 算法分析与设计实验场

每个范式挑一个代表算法，**答案必须和"把定义直接翻译成代码"的笨办法对得上**，
规模只用来检查"实测增长与理论同阶吗"，不当作正确性依据，也不当作复杂度证明。

五个范式：分治（归并数逆序对）、动态规划（0/1 背包）、贪心（区间调度）、
回溯（N 皇后）、图（Dijkstra + Bellman-Ford/Floyd 参照）。

## 运行

```
run.bat                    # 自测（57 项，0.4 秒）+ 演示（含 quick 档计时，约 4 秒跑完）
python tests\test_algo.py   # 只跑自测
python demo.py              # 只看演示：DP 表、三种贪心对照、N 皇后棋盘、Dijkstra 每轮快照
python experiments.py       # 完整计时档（约 45 秒），README 的数字来自这里
python experiments.py --quick
```

只吃标准库，无安装步骤；实验只在本机算，不联网。

| 空间压缩与循环方向 | `dp.knapsack_rolling` | 倒序保证 `f[w-wt]` 仍是"上一件物品之前"的值 | 与全表逐组相等；正序版单独测出"同一件被装两次" |

| 最优子结构的边界 | `greedy.ratio_greedy_01` | 0/1 背包没有"取前缀即最优"的子结构 | CLRS 反例：比值贪心 160 vs DP 220 |
| 回溯剪枝与撤销 | `backtrack.solve_n_queens` | 不变式：进入第 r 行时前 r 行互不攻击且集合恰为其占用 | N=1..9 与已知解数表；每个解用独立 `is_solution` 复检 |

## 正确性论证（摘要；完整版在各模块 docstring 里）

**分治**：逆序对按"两端所在半区"分成三类，前两类递归，第三类在合并时统计。
合并的每一步，右块元素先出时它比左块剩余元素都小，而这些剩余元素原下标都在它之前——
一次加 `mid-i`。**等号方向是论证的一部分**：`a[i] <= a[j]` 让相等元素保持左块先出，
所以相等不计；写成 `<` 就把 `[7,7]` 算成逆序对。

**DP**：对 `(i, w)` 归纳。`f[i][w]` 的最优解要么不含第 i 件（= `f[i-1][w]`），
要么含它（= `f[i-1][w-wt_i] + v_i`），两种情况都落在更小的子问题上，故取 max 正确。
一维滚动时倒序遍历 w 才能读到"上一行"的值；正序读到的已经是本行更新后的值，
于是同一件物品被重复装入——这是 0/1 背包与完全背包的唯一区别，一行循环方向。
还原方案靠 `f[i][w] != f[i-1][w]`：价值非负时"不相等"只能来自"选了第 i 件"。

**贪心（交换论证）**：设贪心第一个选 `g`，某最优解第一个选 `o`。`g` 是全体里结束最早的，
故 `end(g) ≤ end(o)`；把 `o` 换成 `g`，后面的任务开始时间不早于 `end(o) ≥ end(g)`，仍不冲突，
所以存在"以 g 开头"的最优解。对剩余区间归纳即得。
另外两条直觉**不满足**这个替换条件：按开始时间选到的可能是很长的区间，按时长选到的
可能卡在两个长区间中间——`smallest_counterexample()` 用穷举把最小失败输入找出来，
不是我随口编的：按开始时间最早失败于 `((0,3),(1,2),(2,3))`，按时长最早失败于 `((0,2),(2,3))`。

**回溯**：进入 `search(r)` 时前 r 行已放好且互不攻击，`cols/diag_a/diag_b` 恰是它们的占用。
被这三个集合挡住的列一定与某个已放棋子冲突，所以剪掉的子树里没有解（剪枝不丢解）；
每行恰好放一个、列不重复，故搜索树里每个合法叶子对应唯一解，不重不漏。
对角线公式 `r-c`、`r+c` 各标识一条线；撤销顺序与放置严格相反，少删一个元素等于给下一层留下幽灵占用。

**图（Dijkstra）**：反证。设取出 `u` 时 `dist[u]` 不是最短路长度，取一条真实最短路，
它必然先经过某个尚未确定的点 `x`；由于 `u` 是当时堆里最小的，`dist[x] ≥ dist[u]`，
而边权非负，`s→…→x→…→u` 的长度 ≥ `dist[x] ≥ dist[u]`，与"更短"矛盾。
**非负权是这个论证唯一依赖的前提**，所以负权输入直接抛 `NegativeWeight`，不给错误答案。
Bellman-Ford 不依赖它：`|V|-1` 轮松弛覆盖任意简单路径（最多 `|V|-1` 条边），
第 `|V|` 轮还能改进就说明路径不是简单的，即存在可达负环。

## 实测规模（完整档，2026-09-30 本机运行）

环境：Windows 11 (10.0.26200) / Intel64 Family 6 Model 183 / 24 逻辑核 / Python 3.12.3 /
`time.perf_counter`，每档取中位数，随机数据固定 `seed=20260930`，输入在计时之外准备好。

| 实验 | 规模区间 | 中位耗时区间 | 实测增长 | 理论 | 一句话 |
|---|---|---|---|---|---|
| 逆序对 · 分治 | n 1万 → 8万 | 18.5 → 177.5 ms | log-log 斜率 **1.09** | n log n | 翻倍倍率 2.09~2.15，正是 log 那一小笔利息 |
| 逆序对 · 暴力 | n 200 → 1600 | 0.93 → 69.9 ms | 斜率 **2.08** | n² | 同一实现两套输入，斜率差了整整一个数量级的趋势 |
| 0/1 背包 · DP | n 200 → 1600（W=2000） | 37 → 305 ms | 斜率 **1.02** | n·W，W 固定 → 线性 | 线性看着漂亮，但 W 变大它是**伪多项式**（见局限） |
| 0/1 背包 · 枚举子集 | n 10 → 18 | 1.05 → 356 ms | 每 +2 倍率 **4.3/4.4/4.3/4.3** | 2^n | 4× 一档，n=30 就是十亿级——DP 存在的理由 |
| 区间调度 · 贪心 | n 5千 → 4万 | 1.8 → 21.0 ms | 斜率 **1.17** | n log n（排序主导） | 贪心快不是因为聪明，是因为只做了一次排序 |
| N 皇后 · 集合版 | n 7 → 11 | 0.53 → 196 ms | 倍率 3.8~5.0 | 指数 | 多两档就要等几十秒，n=12 以上演示不再跑 |
| N 皇后 · 位运算 | n 9 → 14 | 2.5 → 9326 ms | 最后一档倍率 5.89 | 指数 | 同一问题的常数级改良，改变不了量级 |
| Dijkstra · 稀疏 E≈2V | V 2000 → 16000 | 5.0 → 41.3 ms | 斜率 **1.03** | E log V | 近乎线性，这就是它敢用于路由的原因 |
| Dijkstra · 稠密 E≈V²/4 | V 300 → 900 | 12.3 → 161 ms | 斜率 **2.33** | V² log V | 稠密时瓶颈在边数，不在堆 |
| Bellman-Ford · 随机图 | V 400 → 3200 | 1.1 → 14.3 ms | 斜率 **1.20** | 最坏 V·E | **斜率小于理论**：它一轮没改进就收敛了 |
| Bellman-Ford · 链式图 + 边倒序 | V 300 → 2400 | 5.1 → 305 ms | 斜率 **1.96** | V·E（E≈V）→ V² | 换成最坏输入，Θ(V·E) 才现形；V=2400 那档 Dijkstra 快 **291 倍** |

内存实测（n=1600、W=2000、`tracemalloc` 峰值）：DP 全表 **48.5 MB**，一维滚动 **0.1 MB**，
两者答案都是 19914。**但滚动数组丢了方案还原**——省内存和还原方案之间必须选一个，
这不是实现细节，是 DP 设计的取舍。

最后一行值得多看一眼：同一份代码在随机图和 adversarial 链式图上斜率差 0.8。
**计时实验的结论主要由输入形状决定**，所以每张表都必须写清输入是怎么造的。

## 踩过的坑（本轮真实记录）

1. **三种图实现各用各的"边方向"约定**（真 bug）：Dijkstra 与 Floyd 把边表当无向（各自补一条反向边），
   Bellman-Ford 按有向松弛。200 组随机图对拍里 **118 组不一致**——对拍比的是约定，不是算法。
   现在三个实现一律按有向理解，无向图由调用方显式 `undirected(edges)` 展开；
   稀疏/稠密/链式三档也都用同一份生成函数，避免"各自解释图"。
2. **提前收敛让 Bellman-Ford 的实测斜率只有 1.20**，与理论 V·E 差得远。
   不是实现错，是**随机稀疏图两轮就稳定了**。补上链式图 + 边倒序的最坏输入后实测 1.96。
   教训：写"实测复杂度"之前先问"我这输入能不能触发最坏情况"。
3. **计时把输入生成也算进去了**：`bench.growth(fn, sizes)` 里 fn 自己造数据，测的是"生成 + 算法"。
   实测过偏差有多大：逆序对 n=1 万时含生成 21.2 ms、纯算法 14.7 ms（虚高约 44%），
   斜率 1.084 vs 1.047。斜率看着没塌，但**绝对数字全灌水**，而对越便宜的算法灌水比例越大
   （贪心、DP 这类扫描型尤其明显）。现在实验一律用 `bench.sweep`：输入先备好，只测算法本体。
4. **演示里 N 皇后棋盘打成了转置**（`placement[col] == row` 写反）：算法没错，
   但打印出来的棋盘和声称的那组解不是同一个——"看得见"的东西错了，等于没演示。
5. **我自己的期望值算错了两次**，都是测试先错、代码没错：
   背包 `[2,2,3,5]/[3,4,4,6]/W=7` 我写 8，实际最优 11（前三件刚好装满）；
   比值贪心我编的 `(10,60),(5,25),(5,25)/W=10` 恰好**等于**最优，必须用 CLRS 的
   `(10,60),(20,100),(30,120)/W=50` 才真的亏（160 vs 220）。
   教训：期望值也要有出处——要么现场算一遍，要么让参照实现给，不能靠印象。
6. **演示数据不演示**：第一版区间调度例子里三种排序键都选出 3 个，看上去"三种都对"。
   换成 `[(0,5),(1,3),(3,6),(5,7),(6,8),(2,4)]`（3 / 2 / 2）才真的把差别摆出来。

## 已知局限（说清楚，不含糊）

* **计时不是复杂度证明**，也没有做平均复杂度分析、摊还分析、下界证明；
  斜率只是"这台机器、这份输入形状"下的趋势。规模档位是为了 45 秒内跑完，不能外推成生产基准。
* **DP 背包是伪多项式**：`O(n·W)` 里的 W 是**数值**，输入按二进制编码时它的位数是 log W。
  W 很大（例如 10⁸）时本实现会直接把内存吃掉——没有值域缩放、没有 FPTAS、没有 meet-in-the-middle。
* **DP 表的内存没有上限保护**（B11 的 HTTP 有硬上限，这里没做等价检查）：
  `n·W` 超过千万格就会开始难受，`knapsack` 不会提前拒绝。
* **回溯 N 皇后**没有对称性剪枝、没有预置首行、没有位运算化的解列举；
  n≥12 只做计数不做列举，n≥15 本机没测过。
* **区间调度只有"最大数量"版本**：带权区间调度（加权时需要 DP，`O(n log n)`）没做；
  机器数不定的多机调度、区间染色也没做。
* **图**：Dijkstra 拒绝负权（不做 Johnson 势函数、不做 A*）；Floyd 是 O(V³) 全源且稠密矩阵存储；
  没有最小生成树、强连通、最大流（练习 4 留给 B2 的结构复用）。
* **逆序对**只做计数，没有输出"每个元素被跨过的对数"这种分布信息；BIT 版本在测试里作为
  独立校验存在，不作为主实现。
* **全部单线程、纯 Python**：没有向量化/并行对比，也没有 `sys.setrecursionlimit` 之外的
  栈深度保护；`divide._sort` 递归深度是 log n，n 到 10⁶ 量级仍安全，但没有显式校验。
* **随机数据固定 seed**：好复现，也因此只覆盖这些轨迹；没做覆盖率或参数扫描意义上的抽样设计。
