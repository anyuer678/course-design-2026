# B30-mini-raft —— mini-RPC、一致性哈希与 Raft 模拟（分布式与云计算）

**课程映射**：分布式与云计算（PLAN 批次 7）。

一句话：把 Raft 的两条安全性约束放进一个**能逐事件检查不变式**的模拟器里跑，
再用真套接字的 mini-RPC 把"TCP 上没有消息边界"这一课补上。

**红线（先说在前）**：这是**单进程事件驱动模拟**，不是一套多进程真集群。
B41 候选③ 之后**快照（日志压缩）与单步成员变更已实现**（口径先写在
`docs/snapshot-membership-spec.md`，实现只做翻译）；Joint Consensus、Pre-Vote、
磁盘持久化与快照分块**没做**——未做完的不宣称"完整 Raft"（清单见"明确不做"）。

## 运行

```
run.bat                    # 四步：unittest 发现 → 直跑测试文件 → 八段演示 → 展示页新鲜度
python -m unittest discover -s tests -v
python tests/test_b30.py   # 直跑本文件 28 项（discover 37 = 28 + 9 展示页）
python demo.py             # 八段演示，数字全部运行时现算
python tools/logdiff.py a.log b.log    # 两次日志规范化比对（唯一规范项=unittest 计时）
python tools/showcase.py --check        # 展示页新鲜度（--write 重生）
```

纯标准库（`socket` / `threading` / `heapq` / `hashlib` / `itertools` / `random` / `json`），
**零下载零安装**。

## 知识点 与 实现 与 怎么被验证

| 知识点 | 落在哪里 | 怎么被验证（不是"跑过了"，是"能失败"） |
|---|---|---|
| TCP 没有消息边界 | `rpc.py` `FrameDecoder` | 两帧粘在一次到达解出 2 条、半帧停在边界（补完才出第 2 条）；坏帧（空行/非 JSON）被跳过且**不回包** |
| RPC 的响应关联 | `RpcClient.call` | 真套接字回声三类请求（含中文与嵌套 dict）；客户端按 `id` 匹配，允许乱序 |
| 哈希分片的代价 | `NaiveShard` vs `ConsistentHash` | 2000 个键实测：朴素取模 4→5 搬 **81.0%**（理论 ≈80%），一致性哈希搬 **23.9%**（理想 1/(n+1)=20%）；且"不属被摘节点却搬家的键 = 0 个" |
| 虚拟副本与均衡 | `ConsistentHash(vnodes=…)` | `vnodes=10` 时三节点负载 `{a:579, b:724, c:697}`（实测，不是断言"应该均匀"） |
| 确定性可复现 | `Simulation(seed)` | 同一 seed 的事件序列与结果逐次一致：`demo.py` 跑两遍输出**逐字相同**（run.bat 日志除计时行外逐字同） |
| Election Safety（一个任期至多一个 leader） | `on_request_vote` 的每任期一票 + 日志新旧比较 | `check_election_safety` 在随机事件流**每个事件后**跑；2400 次检查 0 失败 |
| Log Matching（论文原话） | `on_append` 的 `prev_term` 校验 + 冲突即截断后缀 | 同 index 同任期 → 前缀必须逐条一致；**注入同任期分叉必须被抓**（防止断言被写松）；快照版只在双方日志段都覆盖的区间比（压缩段由哈希链账本兜底） |
| Leader Completeness / §5.4.2 | `_advance_commit` 只推进**本任期**条目 | 构造"旧 leader 被隔离、隔离期收 ghost，多数派选出新 leader 提交 real"，愈合后断言 **ghost 不在任何节点状态机里**、real 全员一致——**一个升级版**：新 leader 压缩**跨过** ghost 索引，旧 leader 必须走 InstallSnapshot 追平（计数器证明），ghost 仍不进任何快照 |
| 状态机安全（含压缩） | `digests` 哈希链账本 | 压缩后旧条目不可见→账本里 `digest(i)=折叠(条目 1..i)`，两节点在共同拥有的最大索引处比一个点即可（任何更早分叉都会改变该值）；账本是**检查器专用**诊断件（不进快照、不参与恢复） |
| 快照与日志压缩 | `_maybe_compact` / 快照字段 | 只压缩**已提交**（压缩点取 last_applied）；日志有界（阈值+余量内）；`verify_node_replay` 校验"状态机 == 快照+日志重放"且账本链接得上——**改坏一条日志它必红** |
| InstallSnapshot | `send_snapshot` / `on_install_snapshot` | leader 发现 `next_index < first_log_index` 改发快照；follower 有"进度只许前进"守卫（陈旧快照连角色/计时器都不碰，有专测）；被压缩节点追上并回放校验 |
| 成员变更（单步） | config 条目 + `effective_members` | 配置是普通日志条目、**提交后生效**；一次一个（有未提交 config 时第二次变更被拒）；新节点空配置不自荐、被移除者学会后安静；3→5→4 新节点追平、缩容后服务未断 |
| 配置安全不变式 | `check_config_overlap` | 相邻配置（含自举→首次）差一个成员 + 单步多数派必相交；**负面对照**：差两个成员必红；"全对全多数派相交"是过强断言——实测反例在注释里（坑 7） |
| 分区与丢包 | `Network.partitioned` | 分区期间丢弃计数（实测 256 次），多数派侧仍可提交、少数派侧不能 |
| 重启与持久化 | `Simulation.restart` | 持久字段（term/voted_for/log/sm/commit/applied/**快照字段与账本**）保留、易失字段清零；重启后重新选出 leader 且已应用前缀只前进（旧前缀 digest 不变） |

## 实测（2026-10-02，`run.bat` 连跑两次）

- 测试：**37 项通过**（15 项原有 + 13 项快照/成员变更 + 9 项展示页；两文件直跑 28 + 9）。
- `run.bat` 两次退出码均 **0**、日志 `not recognized` **0**；两次日志经 `tools/logdiff.py`
  规范化（唯一规范项=unittest 计时 2 条）后**逐字相同**（各 209 行——展示层批次⑥ 补全后按新步数两跑重测）。
- 展示页（展示层批次⑥ 交付、⑩ 补全）：`web/showcase.html` = 选举时间线 + §5.4.2 ghost 覆盖实验 +
  一致性哈希 23.9% vs 81.0% 搬移对比（全部现算）；9 项展示页测试。
  `run.bat` 跑完**一条新文件都没加**（20 条文件里含 `.ruff_cache/` 与 `__pycache__`，
  是历史缓存不是本轮生成）。
- 演示读数（现算）：选举 `seed=0` 在 t=20 选出节点 2（term=1），三条命令后全员 `commit=3`；
  分区场景 `seed=1`（分裂当时旧 leader 节点 2 term=1、新 leader 节点 0 term=2），ghost 无人应用；
  随机事件流 10 seed × 60 步 = 600 个事件 × **4 条不变式 = 2400 次检查 0 失败**，
  期间 **25** 次选举、**256** 次分区丢包、**38** 次成员变更、**137** 次压缩、**60** 次快照安装，
  并对全部节点做了"快照+日志重放"校验；
  重启场景 `seed=3` 重启前后 `(term, 末索引, commit, sm) = (1, 2, 2, {a:1, b:2})` 完全保留，
  t=219 重新选出 leader，旧前缀 digest 不变；
  快照演示 `seed=2`：多数派压缩 7 次、leader 快照到 index=12 且日志剩 0 条，
  被隔离节点落后于多数派日志起点，愈合后走 InstallSnapshot（计数 1 → 2）追平；
  成员变更演示：3 → 5 → 4，两次扩容 True/True、缩容 True，新节点 `sm[k3]=v3`，
  被移除者 `effective_members` 不再含自己，配置史 `[[0,1,2,3],[0,1,2,3,4],[1,2,3,4]]`，
  缩容后仍能提交且剩余成员一致。

## 与 PLAN / ROADMAP 的偏离（如实记）

1. **ROADMAP §3.4 写"多进程 + 重启/分区实验"**：这里做成了**单进程事件驱动模拟**
   （选举/复制/分区/重启都有）+ **一个真套接字的 mini-RPC**（`socket` + 每连接一线程）作为通信层实物。
   理由：模拟器的价值恰在"时间可控、每个事件后能查不变式、同 seed 可复现"，
   真多进程会把这些性质换成 flaky 测试。**没有**偷偷把"多进程"划掉——这条就是记录。
2. **事件时间线导出 HTML**（ROADMAP 的可视化项）**未做**：`sim.timeline` 目前是文本列表。
   没做的原因很简单：一旦交付 HTML，它就需要你在浏览器里实跑验收（本项目已有 B27 卡在这一步），
   我不拿"生成了但没人看过"的东西当完成。列为扩展项。
3. （候选③）**成员变更做的是"单步 + 一次一个"而不是 Joint Consensus**：单步变更是论文里
   被明确论证过的简化路径，前提（一次一个、改前必须提交）两条都代码强制并有测试；
   Joint Consensus 是通用解，明确没做。**发送集用了 committed ∪ effective 的并集**
   （论文口径是只发 latest）：这是可达性工程——让新增节点提前追赶、被移除节点在提交前
   仍能收到条目从而"学会自己已被移除"；安全口径不变（多数派只看 effective/committed）。
4. （候选③）**被移除节点的 disruption 按未修复形态登记**：在它学会配置之前（或一直
   收不到消息时），它可能自认仍是成员并搅动选举（论文 §4.2.3 的问题；工业修复是
   Pre-Vote/CheckQuorum，本模拟不做）。**安全不变式不受影响**，且测试不假设
   变更期间一定有稳定 leader。快照安装**整发不分块**、follower 全弃后缀不保留匹配段——
   两条简化都写在 spec 里。

## 踩过的坑（本轮与历史的真实记录）

1. **不变式被写强了，不是实现有 bug**：`check_log_matching` 第一版要求"任意两节点日志的**公共前缀**逐条相同"，
   `demo.py` 第 5 段在 `seed=5` 当场抛红。查现场：这是**合法中间态**（新 leader 还没覆盖 follower 的
   未提交旧任期条目）。按论文原话改成"同 index 同任期 → 该处及之前逐条相同"，并补三条测试：
   当年 seed 复跑不抛、合法中间态明确放行、**注入同任期分叉必须仍被抓**。
2. **演示读数取错了时刻**：第 4 段最初打印"旧 leader term=2、新 leader term=2"，看起来像"同任期选出两个 leader"，
   其实是愈合后两边收敛了。改成在**分裂那一刻**取任期。
3. **代码注释里留着一条更早的现场**（上一会话记在 `sim.py`）：追加日志按 0 基下标写 `log[-1]`，
   `prev_index=0` 的空日志直接 `IndexError`——Raft 实现的经典翻车点。
4. **交付前体检发现测试文件自身有三处问题**：未用的 `import socket`、未用的变量、
   `wait_leader` 定义两次（后者覆盖前者）。**接手别人写的项目也要重新体检**。
5. **我这轮自己的两次小失手**：Git Bash 吃掉反斜杠；按记忆写 `unittest.main()` 锚点替换静默失效。
6. （候选③）**follower 日志比 leader 长时回执越界**：`on_append_resp` 直接采信
   `match=对方日志总长度` → `next_index` 超过 leader 自己的末索引 → 下一次 `send_append`
   的 prev 查询 `IndexError`（soak 当场炸出）。修法是在 leader 侧钳制
   `min(match, leader.last_log_index())`。**旧代码同源**——重构放大覆盖面后才暴露出来。
7. （候选③）**我又写过强断言，第二次**：`check_config_overlap` 第一版要求"任意两份已提交配置的
   多数派都相交"，churn `seed=5` 撞出 `{0,1,2,3}` 与 `{0,1,3,4,6}`——那是合法的隔步演化
   （单步变更只保证**相邻**配置相交）。改为相邻检查 + 把"全对全过强"的证据写成代数事实单测
   （单步必相交 / 换人不保证）。与坑 1 同一教训：**断言写强会把正确实现判成 bug**——
   这是同一个坑第二次到场，钉在注释里。
8. （候选③）**压缩的读写顺序**：第一版 `_maybe_compact` 先改了 `snapshot_index` 再按旧基点
   算日志切片、读 term——跑之前自查发现（改基点前先把 members/term/digest 全读出来）。
   设计文档先写的好处就在这类地方，翻车点大多是"顺序"。

## 明确不做（不是"以后再说"，是本期范围外）

- **Joint Consensus**（联合作签的通用成员变更协议）：只做单步 + 一次一个的简化路径。
- **Pre-Vote / CheckQuorum**：不做，被移除节点的 disruption 按未修复形态登记（见偏离 4）。
- 多进程真集群、真实网络乱序/重复投递、磁盘持久化与 WAL。
- 快照分块传输（InstallSnapshot 整发）、快照安装时的日志后缀保留优化（全弃 + 续传）。
- 写请求线性化（本章只保证状态机安全与已提交条目不被覆盖）。
- 选做：事件时间线导出 HTML（见偏离 2）。

## 已知局限

- 结论只在"这套 seed 与这套参数"上成立：`t=20` 当选、`81.0% / 23.9%` 等数字是**固定种子的实测值**，
  不是理论界，也不是性能测量（本模拟不测吞吐/延迟，也不该被拿去外推）。
- 分区模型是"组间静默丢弃"，没有拜占庭节点、没有消息篡改与重放。
- 状态机只有 `set` 与 `config` 两种命令，没有条件写入/事务。
- 快照账本（`digests`）是**检查器专用的诊断设施**（每条 32 字节，永不截断），
  真实系统没有它、也不该有——它的存在是为了让"任意时刻的跨节点前缀比较"可检查；
  恢复语义只依赖快照 sm + 日志（`verify_node_replay` 的两半分别对应两者）。
- 成员变更的单步安全性依赖"一次一个 + 改前必须提交"两条前提；它由代码强制并有测试，
  但**隔步配置的链式安全**只有逐事件不变式实测兜底，没有形式化证明（Joint Consensus 才是通用解，未做）。
