# 摘要

课程实践项目以"个人作业"形态散落时，无法进入教学环节：教师不能在课堂上
组织学生在线运行与观察，学生的学习过程无法记录与追溯。本课题设计并实现了
CourseLab 课程工坊——一个面向课堂教学的课程项目平台，把 33 个课程实践项目
升格为可登录、可在线运行、可管理、能部署的教学系统。

平台以 Python 标准库与 SQLite 实现，单进程承载学生、教师、管理三端，零第三方
依赖。设计中贯彻三条原则：**内容源唯一**——课程与项目元数据从仓库现算，
平台数据库只存平台态，内容不漂移；**判定唯一**——角色权限矩阵落成服务端
唯一判定函数，页面只读判定结果；**命令白名单**——在线实验客户端只能选择
服务端写死的"项目 × 动作"条目，从结构上消除任意命令执行。在线实验以子进程
沙箱执行，提供 SSE 实时日志流、并发限额、超时与整树杀、全量运行审计。
练习任务支持完整的提交—批阅闭环：学生提交作业（重交清分），教师打分与
评语（已批可改分），成绩全程留痕。

系统以 145 项端到端自检验证（含越权、跨源、目录穿越、限额等负面用例与
16 类畸形输入探针，全部拒绝且零崩溃），性能实测 200 请求 / 8 并发下
失败恒为 0、p95 < 35ms，吞吐随主机负载在数百 req/s 浮动，满足课堂规模。
平台的自动备份/恢复、日志轮转与配置化部署使其可在教师个人计算机上真实
运行。作为工程背景，课题前期还将课程项目群的代表性引擎升格为八个可由
统一门户管理的真实产品，形成了
"引擎零重写、测试双入口、引数字先复算"的工程纪律，该纪律贯穿平台全程。

**关键词**：课程平台；Web 教学；Python 标准库；SQLite；服务器推送事件；
在线实验；自动化测试

## Abstract（草稿——按学校模板核对格式）

Course-oriented software projects usually remain collections of individual
assignments: they cannot be browsed, run, or managed by a class, and students'
practice is neither observable nor traceable. This thesis presents the design,
implementation and evaluation of CourseLab, a course project platform that
upgrades 33 self-contained course projects into a deployable teaching system
organized as per-course workspaces with online demos, sandboxed experiments,
exercises with a full submission-and-grading loop, and administration.

The platform is implemented entirely with the Python standard library and
SQLite, serving student, teacher and administrator front-ends in a single
process with zero third-party dependencies. Three principles drive the design:
**single source of content** (course metadata is computed from the repository,
the database stores only platform state), **single source of authorization**
(the role matrix is one server-side `can()` function), and a **fixed command
whitelist** (experiment clients can only reference server-defined action ids,
which structurally removes arbitrary command execution). Experiments run in
managed child processes with a concurrency cap, timeout, process-tree kill,
audit records, and live logs streamed over Server-Sent Events.

The system is validated by 145 end-to-end self-checks (2026-10-05: 145 passed,
0 failed), including negative cases for privilege escalation, cross-origin
requests, path traversal and rate limiting, plus 16 malformed-payload probes
across all write endpoints with zero crashes. Under a 200-request / 8-concurrency
benchmark the platform sustains hundreds of requests per second (load-dependent,
p95 below 35 ms) with zero failures, which
is sufficient for classroom-scale use. Automated backup and restore, log
rotation, and configuration-based deployment make it practical to run on a
teacher's personal computer. As prior engineering work, the
repository's representative engines were consolidated into eight
products managed by a unified portal; the engineering disciplines established
there run through this platform: engines are imported, never rewritten; every
deliverable is verified through dual test entries; and every cited number is
recomputed on the day it is cited.

**Keywords**: course platform; web-based teaching; Python standard library;
SQLite; server-sent events; online experiments; automated testing

# 第 1 章 绪论

## 1.1 背景与动机

课程实践是软件工程能力形成的必经环节，但"做过"与"可复用、可教学"之间隔着
一道鸿沟。本课题的起点是一个真实积累的课程实践仓库：33 个覆盖网络协议、数据
存储、算法、系统与信息安全等方向的自包含项目，每个项目都有可运行的代码、
测试与演示页，并形成了"每轮交付可运行闭环 + 证据可复算"的工程纪律。

随着项目数量增长，这些以"个人作业"形态存在的成果暴露出三类问题：**散落**
（没有统一入口与组织）、**不可共享**（演示与实验只能本机运行，进不了课堂）、
**不可管理**（没有账号与记录，练习与实验无法追溯）。把项目群升格为一个
**可登录、可浏览、可在线运行、可管理、能部署**的教学平台，是本课题的直接
动机。

2026 年 10 月，本课题确立了两阶段路线：先把课程项目群中的代表性引擎升格为
**真实产品**（不做演示型界面，做成可登录、可一键启停、可部署、可验收的
服务，形成产品矩阵），再以其中功能最完整的课程平台（CourseLab）为论文主体。
前期工程基础见 1.4 节与附录 A。

面对"把项目群组织进教学"的需求，一个自然的疑问是为何不直接采用现成的通用
课程平台或在线判题系统。对比之后选择自建，理由有三：其一，通用平台以"内容
发布 + 作业判题"为中心，本课题的核心对象却是**已经在仓库里、可以运行的课程
项目群**——把三十三份既有内容逐份迁移进外部系统，会立刻产生"仓库一份、
平台一份"的双份内容，内容漂移与维护成本随之而来；其二，目标部署环境（教师
个人计算机、机房）往往不能自由安装数据库、容器等运行时，重型方案的部署
门槛与实际环境不匹配；其三，在线运行学生提交之外的自有项目代码，需要"固定
命令表 + 限额 + 整树杀"这类贴合本仓库形态的实验沙箱语义，通用判题系统并不
直接提供。前两点催生了"内容源唯一、零第三方依赖"的设计原则（第 3 章），
第三点则决定了在线实验的实现形态（第 4 章）。

# 第 2 章 需求分析

## 2.1 背景与问题定义

本课题的起点是一批真实积累的课程实践项目：33 个覆盖网络、数据、算法、系统、
信息安全等方向的自包含项目，每个项目配有演示页、实验台与练习卡。随着数量增长，
"项目群"的使用方式暴露出三类问题：

1. **散落**：项目各自为政，没有统一的目录、入口与组织方式，找一个项目的
   演示或实验入口要在文件系统里翻找；
2. **不可共享**：演示与实验只能在本机运行，教师无法把"在线跑一个项目"变成
   课堂教学环节，学生无法在浏览器里动手；
3. **不可管理**：没有账号体系，谁做过哪个练习、跑过哪些实验、结果如何，全部
   无法记录与追溯。

问题的本质是：**课程项目群缺少一个"平台层"**——把散落的项目升格为可登录、
可浏览、可在线运行、可管理、能部署的 Web 平台，按课程组织，每门课程独享一个
"小型项目平台"（课程页 / 项目页 / 在线演示 / 实验台 / 练习任务）。

与常见做法不同，本平台**不复制项目内容**：课程与项目的元数据从仓库的
manifest 与各 README **现算**得到（内容源唯一），平台数据库只存平台自己的
状态（发布开关、任务、记录、审计）。仓库改了，平台跟着变，两层按 id 关联。

【图表：现状与平台的关系图——内容源（projects/showcase/g2/manifest）→ 平台层】

三类问题可以还原为教学中的三个典型场景，它们也是后文验收口径的"故事原型"：

- **场景一（课前，对应"不可共享"）**：任课教师为某门课程准备一节上机课，
  希望学生当堂在浏览器里运行仓库中的某个项目演示与测试——没有平台时，这
  意味着逐台机器拷贝代码或教师逐个远程协助；有平台时，教师在课程工作区确认
  项目已发布，学生打开项目页即可在线运行（对应功能点 F4/F5）。
- **场景二（课中，对应"散落"）**：学生按课程进入工作区，从项目列表定位
  实验目标，无需知道项目在文件系统中的位置；演示与实验以页签呈现，入口
  统一（对应 F2/F3）。
- **场景三（课后，对应"不可管理"）**：教师查看本课练习任务的完成率与实验
  参与情况，管理员可在审计中核对每次实验运行的记录（对应 F6/F10/F11/F14）。

三个场景贯穿"教师—学生—管理员"三类角色的协作，构成 2.3 节功能点分组的
现实依据。

## 2.2 角色与权限需求

平台涉及四类角色，权限矩阵先于实现写成表格，并落成服务端**唯一的判定函数**
`can(user, action, target)`——页面只读判定结果，不复制规则（判定唯一源原则，
详见 3.2 节）：

| 能力 | 访客 | 学生 | 教师 | 管理员 |
|---|---|---|---|---|
| 浏览课程/项目/演示 | 可 | 可 | 可 | 可 |
| 注册 / 登录 | 注册 | 登录 | 登录 | 登录 |
| 在线实验（跑演示/测试） | 否 | 可（限流） | 可 | 可 |
| 练习任务 | 否 | 领取/提交 | 布置/查看本课 | 全量 |
| 课程/项目管理 | 否 | 否 | 本课 | 全量 |
| 用户/审计/统计 | 否 | 否 | 本课统计 | 全量 |

矩阵中的"本课"边界是教师权限的关键约束：教师只能管理**绑定给自己**的课程，
不能越权操作其他教师的课程——这一条在自检中有专门的负面用例（越级 403）。

## 2.4 非功能需求

| 维度 | 需求 | 落实方式 |
|---|---|---|
| 零依赖 | 不装任何第三方包，可在无外网环境部署 | Python 标准库 HTTP/SQLite + 原生 JS，零构建 |
| 单进程 | 一个进程承载三端 + API + 实验运行时 | ThreadingHTTPServer + 子进程管理器 |
| 安全默认 | 默认只绑回环，公网显式开启 | config 默认 127.0.0.1；public_mode 开关收紧会话与审批 |
| 可审计 | 治理动作与实验运行全量留痕 | audit 表 + lab_runs 表 |
| 可运维 | 备份/恢复/压测/自启/日志轮转 | tools/ 四件工具 + 日志保留 14 天自动清理 |
| 多端 | 三端同源 Web，不做原生 App | 学生端响应式（≤720px 断点），同一 API |

非功能需求不只写形容词，而是以**可配置的量化参数**落进交付物：会话时长默认
12 小时；单个实验超时默认 600 秒，到点整树杀；实验并发上限默认 2（课堂场景
建议 2–4）；日志落盘保留 14 天自动清理；登录失败限流为同"用户名 + IP"
10 分钟内失败 5 次后拒绝。全部参数集中在 `config.json` 八个配置键中，且
**未知键拒绝启动**——配置手滑静默生效比报错更危险，这一条本身也是对"可
运维"需求的落实（参数口径与 5.5 节部署章一致）。

# 第 3 章 系统设计

## 3.1 总体架构

平台是单进程 Web 系统，自上而下分五层，依赖方向单向：

```
web（三端页面：学生 / 教师 / 管理端，原生 HTML/CSS/JS，零构建）
  │  HTTP + JSON API + SSE
HTTP 服务层（标准库 ThreadingHTTPServer + 自研路由表 + 会话）
  │
领域层（auth / courses / labs / tasks / notices / admin / can —— 判定唯一源）
  │
存储层（SQLite：平台态 + 文件系统：日志/备份/上传）
  │
运行时（子进程管理器：固定命令表、日志环、并发限额、超时与整树杀）
```

选择"单进程 + 标准库"的组合出于三个部署现实：课堂机器往往不能装软件包；
一个教师能运维的系统的复杂度上限很低；SQLite 的单文件形态让备份恢复变成
"复制一个文件"（存储口径见文献 [3]）。代价（并发上限、无 HTTPS）在安全
设计一节如实声明。

## 3.2 概念模型与三条设计原则

**概念模型**：仓库里是"33 门课、每门课一个项目"；平台给每门课程开一个工作区，
工作区固定五块——简介区、项目区、演示与实验（项目页两页签）、练习任务、
资料与公告。

三条设计原则贯穿全部实现：

1. **内容源唯一**：课程/项目/演示/练习的**内容**不落库，每次请求现算自仓库
   （manifest + README + 练习卡）；数据库只存"平台态"（发布/排序/绑定教师/
   任务/记录/审计），两层按 id 关联。收益：内容不会在仓库和数据库之间漂移；
   代价：内容展示无法脱离仓库存在——这是有意的选择（本平台定位是课设仓库的
   "平台层"，不是通用 CMS）。
2. **判定唯一**：2.2 节的权限矩阵落成服务端一个函数 `can(user, action,
   target)`，三端页面的所有能力入口由它驱动渲染，前端不判权限——规则只有
   一份，越权测试有唯一依据。
3. **命令白名单**：在线实验沿用"客户端只能选 `项目 × 动作 id`"的边界——
   命令表在服务端写死，请求带不了任意命令、参数或路径。实验能力的安全性
   由这张表决定，而不是由输入过滤决定。

## 3.3 数据库设计

采用**两层结构**：仓库现算层（课程/项目内容）不落库；平台态层存 12 张表——
8 张核心表（下表）+ 4 张支撑表（讨论区 `posts`/`replies`、通知已读
`notice_reads`、访问计数 `visits`）。核心表如下：

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | username, display_name, role, pwd_hash, pwd_salt, pwd_iter, status | 角色 student/teacher/admin；状态 pending/active/banned |
| `sessions` | token, user_id, expires_at, ip, ua | 登出/改密即失效；过期清扫 |
| `course_meta` | course, published, sort, teacher_id, summary, outline | 覆盖层：发布/排序/绑定教师 + 教师维护内容（旧库自动 ALTER 迁移） |
| `tasks` | course, title, body, due_at, created_by | 教师自建任务；内置任务来自 g2 练习卡（key=course#序号），不落库 |
| `task_records` | task_key, user_id, course, status, note, submission, submitted_at, grade, feedback, graded_at | 状态机 doing/done/submitted/graded；(task_key, user_id) 主键；重交清分 |
| `lab_runs` | user_id, pid, action, kind, started_at, finished_at, exit_code, log_tail | 实验审计与队列的数据源 |
| `admin_audit` | ts, actor_id, action, target, detail | 治理动作全量留痕（角色/状态/课程覆盖/公告/批阅） |
| `notices` | title, body, audience, created_by | 通知与公告 |

设计要点：口令参数（迭代次数）随用户行存——升级成本参数不影响老账号；
`course_meta` 是"覆盖层"而非内容副本（课程简介的现算部分与教师补充部分在
页面并列展示，各自标注来源）；实验审计单独成表并与 `admin_audit`（治理动作）
分离——前者是运行数据，后者是管理行为。

表间关系围绕"账号—行为"两条主线组织：`users` 与 `sessions` 是一对多（一个
用户可同时持有多个会话，改口令即清除其余会话、当前会话保留）；`tasks` 与
`task_records` 是一对多（一个任务多条学生完成记录，删除任务时级联清理记录，
不留孤儿）；`lab_runs` 以 `user_id + pid + action` 记录每一次实验运行，是 F14
队列与审计的数据源；`admin_audit` 与 `notices` 相对独立，分别服务治理留痕与
站内通知。两层模型之间的关联只有 id 引用：`course_meta.course` 对应现算层的
课程 id，内置任务的 `task_key`（course#序号）与 `lab_runs.pid` 对应项目 id——
**平台态表不外键约束现算内容**，因为后者不落库，内容改名或重组
由现算层自然呈现，平台态不随之失效。

## 3.4 接口设计

协议约定：请求与响应均为 JSON；错误统一 `{"ok": false, "error": "...",
"code": "..."}`；状态码语义沿用 HTTP 标准（400 参数 / 401 未认证 / 403 越权 /
404 不存在 / 409 冲突 / 429 限流 / 500 服务器错误）。API 分八组（v1 冻结
24 条，后续里程碑按需扩展，路由以服务端现行为准）：

| 分组 | 路由（摘要） | 覆盖功能点 |
|---|---|---|
| auth | register / login / logout / password、GET me | F1/F7/F16 |
| courses、projects | 课程目录与工作区、项目详情（含动作表） | F2/F3/F4 |
| labs | run / runs/{id} / **runs/{id}/log（SSE）** / stop | F5/F14 |
| tasks | tasks / claim / done / mine / **submit**（交作业） | F6/F7 |
| teacher | courses / course / **submissions（提交列表）** / **grade（批阅）** / tasks / tasks/{id}/delete / course/meta | F9–F11 |
| admin | users / courses / labs / labs/{id}/kill / dashboard | F12–F15 |
| notices | notices / {id}/read | F8 |

**SSE 事件格式**：实验日志流以 `event: log`（逐行日志）与 `event: done`
（退出码与耗时）两类事件推送——相比轮询，SSE 让学生在浏览器里看到"真的
在跑"的过程；相比 WebSocket，SSE 单向语义与实验日志的需求恰好匹配，实现
保持在标准库范围内（事件帧格式见文献 [5]）。

以登录接口为例说明协议形态（示意，与实现一致）：

```text
POST /api/auth/login
{"username": "stu01", "password": "..."}

成功：200，设置会话 Cookie（Set-Cookie），后续请求凭 Cookie 认证
失败：401/429，统一错误体：
{"ok": false, "error": "用户名或口令不正确", "code": "BAD_CREDENTIALS"}
```

SSE 端点（`GET /api/labs/runs/{id}/log`）的响应体由一串事件帧构成，帧格式
与 [5] 一致（`data` 载荷为 JSON 编码，与实现一致）：

```text
event: log
data: "[demo] 自检通过 42/42"

event: done
data: {"exit": 0, "seconds": 12.4, "pid": 812, "action": "demo"}
```

`log` 事件的载荷是 JSON 字符串形式的单行日志；`done` 事件携带退出码
（`exit`）、耗时（`seconds`）与运行元信息，客户端据此把"运行中"切换为
"已完成/失败"状态。

## 3.5 关键机制设计

1. **固定命令表沙箱**：实验的"动作"是服务端写死的 `(项目, 动作 id) → 命令`
   映射，客户端提交的只有 id——任意命令、参数、路径在结构上进不来。运行在
   子进程中执行，带并发限额（默认同时 2 个）、超时与**整树杀**（Windows 与
   POSIX 两套实现，保证不留孤儿进程）。
2. **SSE 日志流**：子进程日志入日志环，SSE 端点按事件边界推送；运行结束补
   `done` 事件；断线可用同一端点回放（自检断言"回放含 log 与 done"）。
3. **现算与覆盖层合并**：课程目录请求到达时现算仓库内容，再与 `course_meta`
   覆盖层合并返回；`catalog()` 以 mtime 做缓存，仓库未变时零重复扫描。
4. **绑定式教师授权**：教师与课程的绑定存 `course_meta.teacher_id`，`can()`
   在"本课"动作上显式校验绑定关系——教师权限的边界是数据，不是约定。
5. **会话生命周期**：Cookie 令牌 + 服务端 `sessions` 表；改口令使该用户其余
   旧会话全部失效（当前会话保留，"改密踢会话"）；过期会话由启动清扫 +
   惰性校验双路径回收。
6. **访问计数口径**：只计页面（`/` 与 *.html），资源与 API 不计——看板的
   "访问量"因此有明确语义（自检含"+2 精确断言"）。
7. **实验就绪判定**：实验进程"是否就绪"不能靠单次探测——子进程刚拉起时
   端口尚未监听，单次探测会把"还没好"误判成"起不来"。设计为**连续稳定
   观察**：连续多次探测成功才判定就绪。该机制的误报路径曾由白盒 A/B 实验
   复现并修复（见 4.8 节与里程碑 M11）。
8. **作业提交状态机**：练习任务的状态机为 `doing → done / submitted →
   graded`。两条防脏数据规则：学生**重交**使记录回到 submitted 并清空原
   分数与评语（教师看到的永远是当前版本）；教师对已批阅记录**重批改分**
   合法（改分是教师权责），但对未提交记录批阅一律 409。批改动作写入审计
   表，谁、何时、给谁、打了多少分可追溯。

## 3.6 安全设计

安全设计遵循"默认不信任，边界显式"（详见 SECURITY.md，五节均可成小节）：

- **网络边界**：默认只绑 127.0.0.1；`public_mode` 打开后收紧会话时长、注册
  转管理员审批、实验并发降为 1，页面常驻安全提示；
- **账号**：口令 PBKDF2-HMAC-SHA256，盐 + 迭代参数入库（口径出自文献 [4]），
  比对用 `hmac.compare_digest` 恒时比较；登录限流（滑窗）；会话可
  服务端强制下线；
- **权限**：`can()` 唯一判定源 + 越权负面用例（越权 403、自封拒绝、未绑定
  403、越级 403）；
- **运行沙箱**：固定命令表 + 并发限额 + 整树杀（见 3.5.1）；
- **注入面**：SQL 全参数化；页面渲染转义；CSRF 基线（SameSite Cookie +
  状态变更要求同源 Origin）。

**如实声明**（第 6 章局限的来源）：无 HTTPS、无 2FA、非容器级隔离、单机
单进程——课堂与可信局域网是设计目标场景，公网部署需要额外的反向代理与
运维能力。

五节安全设计可以收拢为一张威胁模型小结，每条威胁都对应一个**结构性边界**
与一个**负面用例锚点**（测试细节见第 5 章）：

| 威胁 | 结构性边界 | 负面用例锚点 |
|---|---|---|
| 越权访问 | `can()` 判定唯一源，前端不判权限 | 越权 403 / 越级 403 / 未绑定 403 |
| 任意命令执行 | 固定命令表，请求只带动作 id | 动作白名单自检 |
| 口令窃取与穷举 | PBKDF2 + 盐 + 恒时比较 + 登录限流 | 失败 5 次 429；改密踢会话 |
| CSRF | SameSite Cookie + 同源 Origin 校验 | 跨源 POST 403 |
| 注入（SQL/HTML） | 全参数化查询 + 页面转义 | 16 类畸形探针 |
| 资源滥用 | 并发限额 + 超时 + Content-Length 钳制 | 限额 429 自检 |
| 路径穿越 | 静态文件根目录约束 | `/repo/` 越界 404 |

这张表也是安全需求的验收索引：设计上每个威胁都有"结构上挡住"的手段，
测试上每条边界都有一个"这样应该被拒绝"的用例钉住——安全设计不依赖
"写代码时小心"。

## 3.7 部署设计

运行形态为单进程 `python server.py`（默认 `127.0.0.1:7900`），`config.json`
切 bind/port/data_dir/max_labs/session_hours/public_mode。两类目标场景：

- **课堂局域网（主打）**：教师机 `bind: 0.0.0.0`，学生浏览器访问
  `http://<教师机IP>:7900/`，实验并发限 2–4 防止课堂齐跑打爆机器；
- **单人 / 公网试用**：public_mode 收紧会话与审批，README 写明边界与备份要求。

运维面：`tools/backup.py`（`VACUUM INTO` 时间戳副本 + 上传文件清单）、恢复 =
停服替换 + 校验、`tools/bench.py` 压测、开机自启脚本、日志落盘保留 14 天自动
清理。数据目录（data/、logs/、backup/）均不进版本库。

# 第 4 章 系统实现

## 4.1 技术选型与代码组织

技术选型回答"为什么是标准库 + SQLite + 原生 JS"：

- **零下载**：目标部署机（教师机、机房）常不能自由安装软件包；纯标准库意味着
  `python server.py` 就是全部后端，拷贝目录即部署（标准库口径见文献 [2]）；
- **可审计**：不引 Web 框架意味着路由、会话、权限判定都在自己的代码里，安全
  审查（SECURITY.md）可以逐行读完；
- **单进程可部署**：SQLite 单文件 + 单进程 = 备份恢复是文件级操作，不需要
  数据库运维技能。

代码组织即分层（与 3.1 图一一对应）：`server.py`（HTTP 服务：路由、会话、
SSE、请求校验）、`app/` 领域层八模块（db / auth / courses / labs / tasks /
notices / admin / **can**——判定唯一源）、`web/` 三端页面 + 共享资产、
`tools/` 运维四件（backup / restore / bench / 自启脚本）。

## 4.2 账号与会话

- **口令存储**：PBKDF2（盐 + 迭代），且迭代参数随用户行入库——整体提升成本
  参数时不破坏老账号的登录；
- **会话**：登录签发随机令牌写入 Cookie，服务端 `sessions` 表保存
  （token, user_id, expires_at, ip, ua）；管理端可强制下线，改口令使该用户
  **全部**旧会话失效（"改密踢会话"，自检有专项）——语义上"其他会话立即
  失效、当前会话保留"，避免改密者把自己也踢出；改口令时的旧口令校验同样
  计入登录失败限流，防止把改密接口当作穷举旁路；
- **登录限流**：滑动窗口计数，维度为"用户名 + IP"，10 分钟内失败 5 次后
  返回 429（RATE_LIMITED）——按用户名 + IP 而非仅按 IP 计数，使得同一台
  网关后的多名学生互不干扰，同时单个账号的穷举成本仍然陡增；
- **过期回收**：过期会话由两条路径回收——服务启动时全表清扫一次，日常请求
  中惰性校验到期即拒，无需后台常驻任务；
- **状态机**：注册 → pending/active（由注册模式配置决定）→ banned，封禁
  立即下线并级联清会话（负面用例钉住）。

## 4.3 现算内容源与 catalog 缓存

课程/项目/练习内容**不落库**，来自仓库的 manifest 与练习卡（内容源唯一，
见 3.2）。实现上以 `catalog()` 统一供给，并以**文件 mtime 组作缓存键**：
缓存键是 manifest 与练习卡两个文件的 `st_mtime` 组成的二元组（练习卡文件
不存在时取 0），请求到达时先算键、键未变直接返回缓存，键变了才重新扫描
合并——"仓库改了，平台跟着变"的目标由一个纯函数 + 一个键值缓存实现，
没有后台同步任务，也不存在失效通知：**文件系统的时间戳本身就是失效信号**。
缓存的只是"读文件"这一步，覆盖层合并（平台态叠加到现算内容上，页面并列
展示并标注各自来源）仍然每次请求现做，保证发布/排序等平台态的修改立即
可见。

## 4.4 在线实验实现

在线实验是平台风险最高的能力，实现围绕"结构上带不进危险"：

1. **固定命令表**：服务端 `TASKS` / `SERVES` 两张表把 `(项目, 动作 id)` 映射
   到具体命令与展示元数据；API 只收动作 id（`actions` 接口是页面按钮的
   数据源），任意命令/参数/路径在结构上不可达；
2. **运行时**：`Labs` 维护运行中实例表、并发限额（config `max_labs`，默认 2）、
   单实验超时（默认 600 秒）；守护线程监控到期与退出，`atexit` 挂停机清理；
3. **日志环**：每个运行实例持有一个定长队列（`deque(maxlen=4000)`）作为
   日志环——内存占用有上界，长日志自动丢弃最旧行，SSE 与回放共用这一份
   缓冲，不需要临时文件；
4. **整树杀**：实验进程可能是 `cmd /c run.bat` 的批处理链，直接 terminate
   会留下继续跑的子进程（实验台 lab.py 同款教训）——Windows 用
   `taskkill /F /T /PID` 整树强停，POSIX 用 `terminate()`，再等待 + 兜底
   `kill()`，保证"强停 = 真的停了"；
5. **审计**：每次运行的谁/何时/项目/动作/耗时/退出码落 `lab_runs`；运行
   结束时回写 `finished_at`、`exit_code` 与日志尾部（`log_tail`），使得
   管理端在实例从内存清理后仍能查到运行结果；运行中的实例可由管理端
   `labs/{id}/kill` 强停。

## 4.5 SSE 流式日志

实验日志用服务器推送事件（SSE）下发：端点把日志生成器产出的事件写成
`event: <名>\ndata: <JSON>\n\n` 帧并逐帧 flush；两类事件 `log`（逐行日志，
载荷为 JSON 字符串）与 `done`（退出码、耗时与运行元信息）。生成器先从日志
环起点**回放**已产生的行，再跟随实时输出，每 0.25 秒轮询一次新行与结束
状态——订阅者无论何时加入，都能看到从第一行开始的完整日志。运行记录
不存在（平台重启过）时，端点补一条带错误说明的 `done` 事件而不是挂起，
客户端能明确知道"回放不可得"的原因（自检断言"回放含 log 与 done"）。
客户端断开（BrokenPipe / ConnectionReset）静默容忍——跑实验的人关掉页面
不该算错误。

## 4.6 三端页面

学生端（门户/登录注册/课程/项目/任务/个人中心）、教师台、管理端三套页面
同进程托管，共享同一份设计 token（assets/app.js + app.css）与同一个 JSON
API；学生端同一套页面在移动浏览器按响应式断点（≤720px）呈现。页面清单
与信息架构如下（与 3.4 节 API 分组一一对应）：

| 端 | 页面（路径摘要） | 访问门槛 |
|---|---|---|
| 学生 | 门户首页 `/`、登录/注册、课程工作区 `/courses/{code}`、项目页 `/projects/{pid}`（详情/演示/实验三页签）、任务 `/tasks`、个人中心 `/me` | 浏览公开；任务与实验需登录 |
| 教师 | 教师台 `/teacher/`、课程维护、任务与统计 | 教师 |
| 管理 | 总览、用户、课程治理、实验审计与队列、看板 | 管理员 |

门槛语义刻意宽松：课程与项目的**浏览**对未登录访客开放（降低课堂使用
摩擦——学生先看再注册），凡涉及**状态变更**的能力（跑实验、领任务、
治理操作）才要求登录与对应角色。前端对这一边界的呈现是"入口可见、
动作拦截"：访客能浏览项目页并看到实验按钮，点击运行时服务端返回 401
（LOGIN_REQUIRED），页面把"请先登录"的错误语义如实展示——权限的真判定
始终在服务端，页面不复制规则。页面内所有能力入口由 `can()` 的判定结果
驱动渲染（登录后按角色显隐），越权请求即便绕过前端也在服务端拦截
（页面可达性与权限判定的组合由"页面与安全"域自检覆盖）。

## 4.7 数据一致性细节

四处容易出错的状态迁移都以自检钉住：任务完成记录用 **upsert**（重复提交
幂等）；**封禁用户级联清会话**（封禁即下线，不留"已被封还能操作"的窗口）；
**删除任务级联清完成记录**（不留指向已删任务的孤儿记录）；**作业重交清分**
（重交使记录回到待批阅并清空原分数与评语，教师看到的永远是当前版本；教师
改分走重批路径，与重交互不冲突）。

## 4.8 实现过程中的典型问题

实现不是一次写对——M10（健壮性审查）与 M11（并发与清理审查）两个专项
里程碑各抓出并修复了一类问题，每一处修复都固化为回归自检：

1. **实验就绪判定误报**（M11）：子进程刚拉起时端口尚未监听，"单次探测
   端口"会把"还没起好"误报为"起不来"。修复以白盒 A/B 实验定位：同一
   代码路径连续观测两次，观测结果不一致即证明判定依赖了竞态时序；最终
   改为**连续稳定观察**（连续多次探测成功才判就绪），误报消失且用例钉进
   自检。
2. **畸形入参致 500**（M10）：对全部写接口做 16 类类型探针时，发现教师
   绑定接口把非整数的 `teacher_id` 直接透传内部逻辑导致未捕获异常（HTTP
   500，崩溃处理线程）。修复为入参在边界处统一校验——**500 是服务器缺陷，
   4xx 才是拒绝**，此后探针全表 4xx、零崩溃成为常态。
3. **超大请求体**：请求体大小原先不设防，M10 为 Content-Length 加钳制，
   超限请求在读体之前即拒绝，防止内存被单个请求撑爆。

这三个问题的共同点是：它们都不是功能缺陷，而是"被攻击/被误用时系统的
行为"缺陷——恰好落在第 5 章负面用例的覆盖范围里，也说明专项审查里程碑
对交付质量的必要性。

# 第 5 章 系统测试与部署

## 5.1 测试方法学

测试体系沿用课设仓库的既定纪律，四条原则：

1. **负面用例必须"红在该红的原因上"**：每条安全/健壮性需求都配一个"这样
   应该被拒绝"的用例（越权 403、重复领取 409、跨源 403……），断言既查状态
   码也查错误语义——"拒绝"本身不是目的，拒绝的理由才可验证；
2. **测试环境隔离**：自检跑在临时库上（不碰正式数据），可随时反复执行；
3. **断言锚定实测数字**：如访问量"+2 精确断言"、实验退出码逐值比对——
   不接受"看起来成功"；
4. **网络探针显式绕过环境代理**：自检与压测都以 urllib 直连本地服务，但
   Python 默认会把系统代理环境变量带进请求——本机开启代理时，探针会先绕道
   代理服务器再回连本机，产生与被测系统无关的假红（2026-10-05 在自检与
   压测工具中各修复一处）。修复后所有本地探针使用**显式无代理 opener**，
   隔离环境差异。

自检的组织方式是"临时库 + 真服务"：`--selftest` 在临时数据目录上启动真实
HTTP 服务，再以 HTTP 客户端走完整用户路径（注册/登录/跑实验/布置任务/
管理端治理），最后对页面与安全边界逐项断言——测的是**部署出来的系统**，
不是函数级单元拼盘。

2026-10-05 现跑：**145 项全部通过、0 失败**。按功能域分组（口径为成文时
统计，总数当日复核一致）：

健壮性专项（里程碑 M10）：对全部接口做畸形类型探针（16 类：数组当对象、

里程碑把当轮的验收要点与新抓到的缺陷修复各固化为自检项——4.8 节的三个

钉住，防止同类回归。这也是"负面用例红在该红的原因上"的配套纪律：
**每修一个 bug，必补一个让它无法回来的用例**。

## 5.4 性能实测

压测对象选自**公开接口**（无需登录即可访问的混合负载：课程目录 / 课程
详情 / 健康检查），工具为 `tools/bench.py`（标准库线程池并发，显式无代理
直连，输出吞吐与分位延迟）。**2026-10-05 实测**（正式内容源、200 请求 /
8 并发）：

> **779.7 req/s，p50 3.8ms，p95 26.7ms，max 34.9ms，失败 0**

（历史对照：2026-10-04 同口径 458.4 req/s / p50 8.6ms；自检环境同时段
122.6 req/s / p50 18.1ms 作为下限参考。**2026-10-06 在 IDE 与桌面程序
同机负载下复跑三次：223.0 / 371.5 / 385.2 req/s（p50 11–21ms，p95
29–34ms，三次均 0 失败）**——可见吞吐随主机负载浮动，而失败率恒为 0、
延迟始终稳定在毫秒级。结论不受负载影响：**课堂几十人并发的浏览与实验
场景余量充足**——按 p95 34ms 估算，即使全班 40 人同时刷新页面，服务端的
排队延迟也在可感知阈值之下；引用数字当天复算的纪律照旧。）

在线实验路径的性能特征与浏览路径不同：实验是长任务（数百秒）且受并发
限额约束，吞吐压力点不在 HTTP 层而在子进程资源上——这正是并发上限
（默认 2）与超时整树杀存在的意义：HTTP 层的数百 req/s 吞吐（负载相关）
保证的是"页面刷得开"，实验层的限额保证的是"机器不被实验打爆"。

## 5.5 部署与运维

单进程 + SQLite，`config.json` 八项配置（bind/port/data_dir/max_labs/
task_timeout/session_hours/registration/public_mode；**未知键拒绝启动**，
防手滑静默生效）。三类场景：

| 场景 | 配置要点 |
|---|---|
| 本机自用（默认） | 只绑回环；数据/日志/备份全在 data/ |
| 课堂局域网 | `bind: 0.0.0.0` + `registration: approval`（注册待审批）+ `max_labs: 2`；管理端绑定课程给任课教师 |
| 公网/自启 | `public_mode` 提醒收紧；Windows 计划任务 `tools/install_autostart.bat`（非管理员环境如实报错提示提权） |

以课堂局域网（主打场景）为例，一次完整部署的步骤是：

1. 教师机上解压代码目录，`python server.py` 首次启动（默认回环，数据目录
   自动生成）；
2. 编辑 `config.json`：`bind` 改为 `0.0.0.0`、`registration` 设为
   `approval`，重启生效；
3. 产生管理员：先注册一个自己的账号，再以
   `python server.py --promote 你的用户名 admin` 提升；随后在管理端审批
   教师账号并把课程绑定给任课教师；
4. 学生浏览器访问 `http://<教师机IP>:7900/`，注册（进入待审批）→ 管理员
   在"用户管理"中通过 → 登录使用；
5. 课堂实验前在管理端确认实验并发上限与机器负载匹配（默认 2，机器充裕可
   调 2–4）；
6. 此后每日运行一次 `tools/backup.py` 做时间戳备份（或挂开机自启时顺带
   计划任务）。

步骤中没有一步需要安装第三方软件或访问外网——部署门槛被刻意压在
"会改一个 JSON 文件"的水平，这是零依赖选型在部署侧的直接回报。

备份恢复：`tools/backup.py`（SQLite `VACUUM INTO` 时间戳副本 + 完整性校验，
建议课堂场景每日一跑）；`tools/restore.py` 恢复前自动给现存库留底，恢复后
跑一遍自检确认。升级 = 替换代码目录（data/ 不动），表结构由
`CREATE TABLE IF NOT EXISTS` 就地迁移。

课程工作区、项目页与在线演示、在线实验、练习任务与作业提交批阅闭环、
通知公告、用户与课程治理、审计与看板、部署运维全部落地。交付节奏上，
M10/M11 两个里程碑不含新功能、全部投入审查加固——功能做完
不等于交付完成，健壮性与并发行为同样是需求（2.4 节）的一部分；M12 则把
任务能力补全为真实教学闭环（提交、批阅、成绩留痕），消除"功能点有"与
"教学上能用"之间的差距。

**方法线**：三条设计原则贯穿始终并经受了验证——**内容源唯一**（课程内容
现算自仓库，平台库只存平台态，内容不漂移）；**判定唯一**（权限矩阵落成
服务端一个 `can()` 函数，前端不判权限，越权有唯一测试依据）；**命令白名单**
（在线实验客户端只能选动作 id，最大的攻击面在结构上被消除）。

**验证线**：自动化自检 **145 项**（2026-10-05 现跑 145 通过 / 0 失败，
10-06 复跑同绿），其中负面用例覆盖越权、自封、封禁即下线、重复领取、跨源、
目录穿越、限额、批阅边界等安全与健壮性需求；全部写接口通过 16 类畸形类型
探针零崩溃；性能实测（200 请求 / 8 并发）失败恒为 0、p95 < 35ms，吞吐随
主机负载在 223–780 req/s 浮动【10-05/10-06 两日实测】——满足
课堂几十人规模。作为工程背景，课程项目群还完成了"产品矩阵"工程：八个
产品全部成为可一键启停、可探活、有全仓体检的 managed 服务。

## 6.2 局限（如实声明）

局限来自设计目标的选择，如实列出（口径与 SECURITY.md §七 一致）：

1. **单机教学系统**：无 HTTPS、无 2FA、无 WAF；公网裸奔不在设计目标内，
   公网使用应前置 HTTPS 反向代理或限于校园网/VPN；
2. **沙箱非容器级隔离**：在线实验的安全边界是"白名单命令 + 限额 + 整树杀"，
   不是容器/虚拟机隔离——能跑的本来就是平台自己的课程项目；
3. **审计无防篡改链**：管理动作审计覆盖全部管理端变更入口（四类，各有自检），
   但持有数据库文件者可改写记录——单机教学系统的边界，未引入外部日志服务；
4. **单进程与并发韧性**：Python 标准库 HTTP 服务对高并发慢请求的韧性有限
   （量级为课堂规模，见 5.4 实测）；
5. **内容与仓库绑定**：现算是内容唯一口径，脱离课设仓库的平台没有独立
   内容——这是定位使然，通用化属于未来方向。

## 6.3 展望

按投入产出排序的可行方向：

1. **HTTPS 反向代理**：在保持平台零依赖的前提下，用 Nginx/Caddy 前置终结
   TLS，公网部署的最后一块短板；
2. **任务提交式实验**：把"在线运行"从交互式扩展为队列化提交（当前已有
   队列/限额/审计的底座），支持更长时长的批处理实验；
3. **教学闭环延伸**：成绩单导出、课程资料上传、练习与实验成绩联动——
   领域层已按"判定唯一源"组织，扩展不破坏现有权限模型；
4. **多机部署**：当单机 SQLite 不再够用时，把存储层替换为独立数据库——
   领域层与存储层的单向依赖使这一步不动领域代码；
5. **矩阵与平台联动**：产品矩阵的探活/启停能力与 CourseLab 的实验审计
   共享同一批课程引擎，"学生在平台上跑实验"与"运维在门户里管服务"可以
   合并成一套视图。

## 6.4 结束语

本课题最大的收获不是平台本身，而是把"课程作业"升格为"真实工程"的完整
路径：需求先写成可判定的矩阵，设计先写原则再写代码，验证先于宣称，局限
如实声明。这条路径在 33 个课程项目、八个产品与一个平台的连续工程中反复
使用并持续收敛——它比任何单个系统都更接近工程教育的本意。

## 一、从 33 个课程项目到一张产品矩阵

本课题的工程基础是一批课程实践项目：覆盖网络协议（手写 HTTP 服务器、极简
MQTT broker）、数据（迷你 Redis、清洗与挖掘）、算法可视化、Java 面向对象、
信息安全等方向的 33 个自包含项目，每个项目带"编译/自检/演示/展示页"四件套
（run.bat 一键、测试双入口、离屏或无头演示、零外链展示页）。

这些项目最初只是"能跑的作业"。第二阶段把它们升格为**真实产品**——不做
PPT 式演示，而是做成可登录、可一键启停、可部署、可验收的服务（2026-10-04
定调）。最终形成一张由 Studio 门户统一管理的产品矩阵：

| 产品 | 一句话定位 | 引擎来源（零件库） | 测试（双入口） | 服务端口 |
|---|---|---|---|---|
| Studio 门户 | 目录 / 一键启停 / 状态面板 | 自研 webframe（netlab 之上） | 17 | 8017 |
| LinkBox 工具站 | 短链 / 文本暂存 / 文件互传 / 二维码 / 口令 | B31 引擎 + B11 协议层 | 53 | 8018 |
| 展示层实验台 | 33 页展示页的本地控制台 | showcase lab | （并入体检） | 7788 |

| DataScope 工作台 | CSV 画像 / 清洗 / 挖掘 / SVG 报告 | B26 清洗链与 Apriori/K-means | 31 | 8020 |

对应服务并做 TCP 探活；"在线 = 端口连得上"，不撒谎。**已规划清零**——矩阵中
不存在只有名字没有实现的产品。

## 二、零件库纪律：引擎零重写

产品层不重写任何课程引擎，只做编排：产品 = 引擎（import 原项目真实实现）+ 
产品侧新增能力。三例：

- **CacheKV**：KV 语义与快照直接用 B38 的 Store（惰性+主动双策略过期、时钟
  可注入）与 dbsnap（原子写）；产品侧只加统计账本与 HTTP API。
- **SensorHub**：MQTT 全链路（broker、传感器模拟、订阅入库、SVG 曲线）四个
  真件全部来自 B35；产品侧只补阈值告警台账与监测台。
- **Board**：绘图、撤销重做、存档、PNG 导出与全部文件防线来自 B14（Swing 引擎，
  7054 项自检）；产品侧只补 B14 明说自己没有的**自动备份**，外加探活守护。

这条纪律的直接收益是**回归即体检**：引擎完好性由原项目自检钉住（如 B14 的
7054 项检查在产品编译产物上现跑现过），产品测试只盯产品侧新增语义，改动引擎
会立刻红在两处。

## 三、质量基线（可复跑）

1. **测试双入口**：每个产品同时过 pytest 与 unittest discover 两套入口，计数
   必须同源（防"只绿一套"）。
2. **run.bat 两次验收**：一键脚本连跑两次，退出码全 0、目录快照无新增文件、
   输出无静默失败——专治 cmd 的编码与重定向坑。
3. **全仓体检**：`scripts/check_all.py` 15 项一条命令（展示层校验、证据/种子核验、
   事实台账、交付齐全性 + 产品层八件），2026-10-06 全过。
4. **对拍与钉值**：产品语义与"直接调用引擎"逐数对拍；关键数字（自检项数、
   缺口探针、行数锚点）有出处且会过期——改了代码不改文档就红。

## 四、与本平台（CourseLab）的关系

产品矩阵与本论文主体 CourseLab 是同一条"课程实践 → 真实产品"路线的两个阶段：
矩阵证明了课程引擎可以被产品化复用（零重写），CourseLab 则把"课程内容本身"
（33 个项目的演示、实验与练习）升格为可登录、可在线运行、可教学管理的平台。
两者共享同一套工程纪律（测试双入口、自检、原子写、白名单、诚实边界）——
第 5 章的测试方法学在两个阶段同样适用。

## 五、共享设计系统（轮九）

产品矩阵的前端统一收敛到一套设计规范（`courselab/docs/DESIGN-SPEC.md` v2.1，
Geist/Linear 克制工程风：纸白打底、单一强调色、细边框双层阴影、浅色单主题）。
共享样式 `webkit/kb.css` 为唯一源，经同步脚本分发到各产品的静态目录，全仓体检
中的引用扫描会字节级核验新鲜度——改了源不改副本即红。六款 Web 产品的页面均
重排为生产控制台形态（侧边栏导航、高密度数据表、状态胶囊、Toast 反馈），并配
"一键注入演示数据"，使产品打开即是可演示状态；桌面端 Board 画板改用 Nimbus
外观（引擎 App.java 一行显式 setLookAndFeel；此前的 JVM 参数注入方案因被
显式调用覆盖而作废，经真窗口截图复验生效）。该轮改造不触碰任何引擎逻辑——
观感统一的代价被压缩为纯前端工作。
