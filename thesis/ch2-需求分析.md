## 2.1 背景与问题定义

本课题的起点是一批真实积累的课程实践项目：33 个覆盖网络、数据、算法、系统、
信息安全等方向的自包含项目，每个项目配有演示页、实验台与练习卡。随着数量增长，
"项目群"的使用方式暴露出三类问题：

1. **散落**：项目各自为政，没有统一的目录、入口与组织方式，找一个项目的
   演示或实验入口要在文件系统里翻找；
2. **不可共享**：演示与实验只能在本机运行，教师无法把"在线跑一个项目"变成
   课堂教学环节，学生无法在浏览器里动手；
3. **不可管理**：没有账号体系，谁做过哪个练习、跑过哪些实验、结果如何，全部
   无法记录与追溯。

问题的本质是：**课程项目群缺少一个"平台层"**——把散落的项目升格为可登录、
可浏览、可在线运行、可管理、能部署的 Web 平台，按课程组织，每门课程独享一个
"小型项目平台"（课程页 / 项目页 / 在线演示 / 实验台 / 练习任务）。

与常见做法不同，本平台**不复制项目内容**：课程与项目的元数据从仓库的
manifest 与各 README **现算**得到（内容源唯一），平台数据库只存平台自己的
状态（发布开关、任务、记录、审计）。仓库改了，平台跟着变，两层按 id 关联。

【图表：现状与平台的关系图——内容源（projects/showcase/g2/manifest）→ 平台层】

三类问题可以还原为教学中的三个典型场景，它们也是后文验收口径的"故事原型"：

- **场景一（课前，对应"不可共享"）**：任课教师为某门课程准备一节上机课，
  希望学生当堂在浏览器里运行仓库中的某个项目演示与测试——没有平台时，这
  意味着逐台机器拷贝代码或教师逐个远程协助；有平台时，教师在课程工作区确认
  项目已发布，学生打开项目页即可在线运行（对应功能点 F4/F5）。
- **场景二（课中，对应"散落"）**：学生按课程进入工作区，从项目列表定位
  实验目标，无需知道项目在文件系统中的位置；演示与实验以页签呈现，入口
  统一（对应 F2/F3）。
- **场景三（课后，对应"不可管理"）**：教师查看本课练习任务的完成率与实验
  参与情况，管理员可在审计中核对每次实验运行的记录（对应 F6/F10/F11/F14）。

三个场景贯穿"教师—学生—管理员"三类角色的协作，构成 2.3 节功能点分组的
现实依据。

## 2.2 角色与权限需求

平台涉及四类角色，权限矩阵先于实现写成表格，并落成服务端**唯一的判定函数**
`can(user, action, target)`——页面只读判定结果，不复制规则（判定唯一源原则，
详见 3.2 节）：

| 能力 | 访客 | 学生 | 教师 | 管理员 |
|---|---|---|---|---|
| 浏览课程/项目/演示 | 可 | 可 | 可 | 可 |
| 注册 / 登录 | 注册 | 登录 | 登录 | 登录 |
| 在线实验（跑演示/测试） | 否 | 可（限流） | 可 | 可 |
| 练习任务 | 否 | 领取/提交 | 布置/查看本课 | 全量 |
| 课程/项目管理 | 否 | 否 | 本课 | 全量 |
| 用户/审计/统计 | 否 | 否 | 本课统计 | 全量 |

矩阵中的"本课"边界是教师权限的关键约束：教师只能管理**绑定给自己**的课程，
不能越权操作其他教师的课程——这一条在自检中有专门的负面用例（越级 403）。

## 2.3 功能需求（F1–F18）

功能点共 18 个，全部编号（编号即开发里程碑的跟踪单位），分四组：

**学生端（F1–F8）**

| 编号 | 功能 | 要点 |
|---|---|---|
| F1 | 注册/登录/登出 | 口令 PBKDF2（盐+迭代）；Cookie 令牌 + 服务端会话表（可强制下线）；登录限流 |
| F2 | 门户首页 | 平台概览 + 课程目录（搜索/筛选），内容现算 |
| F3 | 课程工作区 | 每课一个工作区：简介区/项目区/演示与实验/练习任务/资料公告 五块 |
| F4 | 项目页 | 详情 + 在线演示（嵌入自包含展示页）+ 在线实验 三页签 |
| F5 | 在线实验 | "项目 × 动作"白名单点选；SSE 实时日志流；结果与耗时落审计 |
| F6 | 练习任务 | 内容源自练习卡；领取 → 完成/提交作业 → 教师批阅（分数+评语）→ 成绩留痕 |
| F7 | 个人中心 | 我的任务、我的实验记录、修改口令（改后其他会话即失效） |
| F8 | 通知与公告 | 未读计数、列表、已读标记 |

**教师端（F9–F11）**：F9 课程维护（补充简介/大纲/发布开关，覆盖层写回平台库，
课程元数据本身仍现算）；F10 任务布置与查看（内置任务挂练习卡 id；批阅提交的
作业：0-100 分 + 评语，已批可改分）；F11 本课
统计（完成率、批阅进度、实验排行按人聚合、最近活动，限本人课程）。

**管理端（F12–F15）**：F12 用户管理（注册审批/角色调整/封禁解封，封禁即下线）；
F13 课程与项目治理（上下架/排序/教师绑定）；F14 实验审计与队列（全量运行记录、
并发限额默认 2、运行中可强停）；F15 平台看板（访问量/实验/任务/活跃用户，
手写 SVG 不引图表库）。

**平台底座（F16–F18）**：F16 会话与安全边界（`can()` 判定唯一源、默认只绑回环、
CSRF 基线）；F17 备份与恢复（SQLite `VACUUM INTO` 时间戳副本，恢复 = 停服替换
+ 校验）；F18 部署与配置（config.json、双入口、开机自启、日志落盘保留 14 天）。

**功能点与里程碑的映射**：18 个功能点不按"一次做完"推进，而是分装进
M0–M12 共 13 个里程碑，每个里程碑都有可机验的验收要点——功能点编号即开发
进度的跟踪单位。映射关系如下（里程碑覆盖的功能点据 DESIGN §八）：

| 里程碑 | 覆盖功能点 | 验收要点（摘要） |
|---|---|---|
| M0 骨架 | — | 自检 4 项起步；现算目录 33 项 |
| M1 账号与会话 | F1、F16（会话） | 注册/登录/登出端到端；越权负面用例 |
| M2 目录与项目页 | F2/F3/F4 | 33 门课可浏览；协议 v1 冻结 |
| M3 在线实验 | F5、F14（队列） | SSE 日志滚动；并发限额与整树杀 |
| M4 任务闭环 | F6/F10/F11 | 布置→领取→完成全链路 |
| M5 多端补全 | F7/F9/F12/F13/F15 | 三端可用；看板手写 SVG |
| M6 部署与素材 | F16 审批/F17/F18 | 备份/恢复演练；课堂真机演示 |
| M7 收官补全 | F8、审计、响应式 | 通知可见性 403；四类动作留痕 |
| M8 授权补全 | F7 改密、F9 维护 | 改密踢会话；旧库 ALTER 迁移 |
| M9 对账补全② | F11/F14/F15/F18 | 访问量 +2 精确断言；日志 14 天清理 |
| M10 健壮性审查 | 全部写接口 | 16 类畸形探针 4xx 零崩溃 |
| M11 并发与清理 | 实验台、会话 | 就绪判定误报修复；会话启动清扫 |
| M12 作业提交与批改 | F6/F10 | 提交—批阅—成绩留痕闭环；重交清分；负面六条 |

值得注意的是 M10、M11 两个里程碑不含新功能，全部投入健壮性与并发清理的
专项审查——"先功能、后加固"的节奏在需求阶段即已规划。M12 则是把任务能力
从"领取/完成状态翻牌"补全为真实教学闭环（提交、批阅、成绩留痕）——功能
点的"有"与"能用"之间的差距，由这类收尾里程碑消除。

## 2.4 非功能需求

| 维度 | 需求 | 落实方式 |
|---|---|---|
| 零依赖 | 不装任何第三方包，可在无外网环境部署 | Python 标准库 HTTP/SQLite + 原生 JS，零构建 |
| 单进程 | 一个进程承载三端 + API + 实验运行时 | ThreadingHTTPServer + 子进程管理器 |
| 安全默认 | 默认只绑回环，公网显式开启 | config 默认 127.0.0.1；public_mode 开关收紧会话与审批 |
| 可审计 | 治理动作与实验运行全量留痕 | audit 表 + lab_runs 表 |
| 可运维 | 备份/恢复/压测/自启/日志轮转 | tools/ 四件工具 + 日志保留 14 天自动清理 |
| 多端 | 三端同源 Web，不做原生 App | 学生端响应式（≤720px 断点），同一 API |

非功能需求不只写形容词，而是以**可配置的量化参数**落进交付物：会话时长默认
12 小时；单个实验超时默认 600 秒，到点整树杀；实验并发上限默认 2（课堂场景
建议 2–4）；日志落盘保留 14 天自动清理；登录失败限流为同"用户名 + IP"
10 分钟内失败 5 次后拒绝。全部参数集中在 `config.json` 八个配置键中，且
**未知键拒绝启动**——配置手滑静默生效比报错更危险，这一条本身也是对"可
运维"需求的落实（参数口径与 5.5 节部署章一致）。

## 2.5 用例与验收口径

需求的可验证性是本平台的硬要求：**每个功能点的验收 = 一组可机验的自检项**。
平台交付时自检共 145 项（`python server.py --selftest`，2026-10-06 现算），
按域分组：账号与会话 23 / 课程与内容 21 / 实验 11 / 任务 29 / 管理端 22 /
部署与工具 12 / 通知与审计 12 / 页面与安全 15。其中负面用例（越权 403、
自封拒绝、封禁即下线、重复领取 409、跨源 403、目录穿越 404、限额 429 等）
构成"系统在被攻击时的行为"需求的一部分——第 5 章测试将逐组展开。

验收文化沿用课设仓库的既定纪律：每轮交付必须可运行、可验证、证据可复算，
不接受"看起来能用"。
